# OpenClaw Role — MVP v1

## 1. Назначение документа

Этот документ определяет роль OpenClaw в архитектуре сервиса недвижимости.

OpenClaw используется как **агент сбора, проверки и актуализации внешних данных**, но не как центральный «мозг» продукта.

Главный принцип:

> OpenClaw ищет и извлекает данные.  
> Нормализация приводит их к единой модели.  
> Deduplication объединяет дубли.  
> Matching Engine решает, насколько объект подходит пользователю.  
> LLM объясняет результат человеческим языком.

OpenClaw не должен самостоятельно решать:

- какой объект лучше для пользователя;
- какой процент соответствия поставить;
- считать ли рекламу подтверждённым фактом;
- подходит ли пользователь под ипотеку;
- является ли юридически безопасной сделка;
- какие пользовательские требования можно проигнорировать.

---

# 2. Место OpenClaw в общей архитектуре

Базовый pipeline:

```text
Внешние источники
      ↓
OpenClaw / API / feeds / connectors
      ↓
Raw Collection Layer
      ↓
Normalization
      ↓
Source & Evidence Layer
      ↓
Deduplication
      ↓
Unified Property Database
      ↓
Matching Engine
      ↓
Explanation Layer
      ↓
Пользователь
```

OpenClaw находится **до бизнес-логики выбора**.

Он является одним из способов получения данных, а не единственным каналом.

---

# 3. Почему OpenClaw нужен проекту

Основная проблема продукта — данные находятся в разных местах:

- сайты застройщиков;
- сайты конкретных ЖК;
- классифайды;
- агентские сайты;
- банковские страницы;
- страницы ипотечных программ;
- страницы акций;
- каталоги домов;
- пользовательские ссылки;
- документы;
- другие доступные источники.

Причём страницы могут быть:

- динамическими;
- JavaScript-heavy;
- непоследовательными;
- без API;
- с нестандартной структурой.

OpenClaw может выступать браузерным агентом там, где простой HTTP-fetch или API недостаточен.

---

# 4. OpenClaw — не единственный способ сбора

Система должна поддерживать несколько методов:

```text
API
partner feed
XML / JSON feed
direct HTTP fetch
browser automation
OpenClaw
manual import
user-provided URL
manual expert verification
```

Приоритет:

> использовать самый стабильный, быстрый, экономичный и допустимый способ.

OpenClaw используется, если:

- нет удобного API;
- страница требует браузера;
- данные появляются только после взаимодействия;
- структура сложная;
- нужно открыть несколько связанных страниц;
- необходимо проверить конкретное условие.

---

# 5. Основные режимы работы OpenClaw

Для MVP предусматриваем четыре режима.

## 5.1. Scheduled Collection

Регулярный фоновый сбор.

Пример:

```text
каждые 6 часов:
- проверить цены;
- проверить наличие;
- обновить акции;
```

Это предпочтительный режим для массовых данных.

Пользовательский запрос не должен запускать полный обход десятков сайтов каждый раз.

---

## 5.2. Targeted Refresh

Точечная перепроверка конкретных полей.

Пример:

Пользователь открыл объект перед финальным сравнением.

Система знает:

```text
Цена — stale
Наличие — stale
ПВ 0 — claimed
```

OpenClaw получает:

```text
Обновить:
- цену;
- наличие;
- ПВ.

Не собирать заново:
- площадь;
- этаж;
- адрес.
```

---

## 5.3. User URL Ingestion

Пользователь вставляет ссылку.

OpenClaw:

1. открывает страницу;
2. определяет источник;
3. извлекает данные;
4. формирует evidence;
5. передаёт данные в Normalization;
6. запускается Deduplication;
7. объект добавляется к сравнению.

---

## 5.4. Search Fallback

Используется, если в собственной базе недостаточно данных для ответа.

Пример:

> Пользователь ищет объект в городе, где база пока неполная.

OpenClaw может выполнить ограниченный целевой поиск по разрешённым источникам.

Этот режим не должен заменять основной data pipeline.

---

# 6. Главная стратегия MVP

Для первой версии нельзя строить архитектуру:

```text
пользователь написал запрос
→ OpenClaw пошёл на 30 сайтов
→ пользователь ждёт
→ агент возвращает ответ
```

Предпочтительная модель:

```text
OpenClaw заранее обновляет базу
        ↓
пользовательский запрос
        ↓
Matching Engine работает по нормализованным данным
        ↓
если критическое поле устарело
        ↓
targeted refresh
```

Это:

- быстрее;
- стабильнее;
- дешевле;
- лучше тестируется;
- позволяет хранить историю;
- позволяет делать deduplication;
- позволяет сравнивать результаты между пользователями.

---

# 7. Что OpenClaw получает на входе

OpenClaw не должен получать расплывчатое:

> «Найди всё про этот ЖК».

Он получает `CollectionTask`.

Рекомендуемая структура:

```yaml
collection_task:
  task_id:
  mode:
  source_id:
  urls:
  entity_type:
  target_entity_id:
  requested_fields:
  freshness_requirements:
  extraction_schema:
  priority:
  deadline:
```

---

# 8. Типы CollectionTask

`mode`:

- `discover`
- `collect`
- `refresh`
- `verify`
- `ingest_user_url`
- `monitor_changes`

## discover

Найти потенциальные страницы / объекты.

## collect

Собрать структуру объекта.

## refresh

Обновить динамические поля.

## verify

Проверить одно конкретное условие.

## ingest_user_url

Разобрать пользовательскую ссылку.

## monitor_changes

Проверить, изменилось ли значение.

---

# 9. Extraction Schema

Каждая задача должна определять, какие поля нужны.

Пример для квартиры:

```yaml
requested_fields:
  - development_name
  - developer
  - address
  - building
  - unit_number
  - rooms
  - total_area_m2
  - floor
  - listing_price
  - availability_status
  - finishing_type
```

Пример для финансирования:

```yaml
requested_fields:
  - family_mortgage
  - min_initial_payment
  - zero_initial_payment
  - interest_rate
  - promotion_valid_until
  - price_impact
```

---

# 10. Принцип минимального сбора

OpenClaw не должен каждый раз извлекать всю страницу во все возможные поля.

Если требуется:

```text
обновить цену
```

сбор должен быть направлен прежде всего на цену и данные, необходимые для её правильной интерпретации.

Это уменьшает:

- время;
- стоимость;
- вероятность ошибки;
- нагрузку на внешний источник.

---

# 11. Raw Data vs Normalized Data

OpenClaw возвращает **сырой результат извлечения**.

Он не обязан полностью приводить его к внутренней canonical-модели.

Пример:

Источник пишет:

```text
2Е, 47,3 м², предчистовая
```

OpenClaw может вернуть:

```yaml
rooms_raw: "2Е"
area_raw: "47,3 м²"
finishing_raw: "предчистовая"
```

Normalization Layer уже приводит:

```yaml
layout_type: euro_two
total_area_m2: 47.3
finishing_type: pre_finish
```

OpenClaw может дать candidate normalization, но окончательное значение должно проходить правила нормализатора.

---

# 12. Что OpenClaw обязан возвращать

Для каждого найденного факта:

- имя поля;
- raw value;
- parsed value, если возможно;
- URL;
- timestamp;
- evidence;
- extraction confidence;
- предупреждения;
- контекст применимости.

Пример:

```json
{
  "field": "listing_price",
  "raw_value": "4 890 000 ₽",
  "parsed_value": 4890000,
  "source_url": "https://example.ru/flat/145",
  "collected_at": "2026-08-12T23:00:00+03:00",
  "evidence_text": "Стоимость квартиры 4 890 000 ₽",
  "extraction_confidence": 0.99
}
```

---

# 13. Evidence — обязательное требование

Для критичных полей OpenClaw не должен возвращать только значение.

Плохо:

```yaml
zero_initial_payment: true
```

Правильно:

```yaml
zero_initial_payment:
  value: true
  evidence_text: "Ипотека без первоначального взноса"
  url: ...
  collected_at: ...
```

Это позволяет Source Layer определить:

```text
claimed / confirmed / unconfirmed
```

---

# 14. Extraction Confidence ≠ Verification Confidence

Очень важное правило.

OpenClaw может быть уверен на 99%, что прочитал текст:

> «Без первоначального взноса».

Но это не означает, что:

- акция действует сейчас;
- она относится к конкретной квартире;
- цена остаётся прежней;
- пользователь подходит;
- банк согласует сделку.

Поэтому:

```text
extraction_confidence = 0.99
```

может существовать одновременно с:

```text
verification_status = claimed
```


# 18. Сбор финансовых программ

Отдельная задача.

OpenClaw должен собирать:

- название программы;
- банк / поставщик;
- тип;
- ставка;
- ставка «от» или конкретная;
- первоначальный взнос;
- сумма кредита;
- срок;
- категория объекта;
- ограничения;
- срок действия;
- обязательные услуги;
- цена при программе;
- источник;
- evidence.

Не переносить условия автоматически на объект.

---

# 19. Сбор акций

Акция должна собираться как отдельная сущность.

OpenClaw должен определить:

- название;
- застройщик;
- ЖК;
- корпус;
- список применимых объектов, если указан;
- период действия;
- скидку;
- влияние на цену;
- влияние на ПВ;
- условия;
- банк;
- ограничения;
- source URL.

Если применимость к конкретной квартире не указана:

```text
property_eligibility = unknown
```

---

# 20. Навигация по связанным страницам

OpenClaw может переходить:

```text
карточка квартиры
→ страница ЖК
→ страница акции
→ ипотечная страница
```

Но должен сохранять происхождение каждого поля.

Нельзя смешивать:

```text
цена из карточки квартиры
```

и:

```text
ПВ 0 с общей страницы акции
```

так, будто они подтверждены одной сущностью.

---

# 21. Multi-step Verification

Пример задачи:

> Проверить ПВ 0 по квартире №145.

OpenClaw может:

1. открыть квартиру;
2. найти связанную акцию;
3. открыть условия;
4. проверить проект;
5. проверить корпус;
6. проверить ограничения;
7. найти банк;
8. вернуть structured evidence.

Но финальный `verification_status` назначает Source / Financing Layer по правилам.

---

# 22. Change Detection

OpenClaw должен уметь сообщать не только текущее значение, но и изменение.

Пример:

```yaml
field: listing_price
old_value: 5050000
new_value: 4890000
change_detected: true
```

Дальше история сохраняется в базе.

---

# 23. Важные динамические поля

Приоритет мониторинга:

1. availability;
2. listing price;
3. reservation status;
4. promotions;
5. initial payment;
6. mortgage program applicability;
7. installment terms;
8. handover dates.

Статические поля не требуется перепроверять так же часто.

---

# 24. Refresh Queue

Рекомендуемая архитектура:

```text
Data Quality Layer
      ↓
Refresh Required
      ↓
Refresh Queue
      ↓
OpenClaw Worker
      ↓
New Evidence
      ↓
Normalization / Source Update
```

---

# 25. Приоритет задач

`priority`:

- `critical`
- `high`
- `normal`
- `low`

### critical

Пользователь рассматривает объект сейчас, а ключевое финансовое условие stale.

### high

Цена / наличие shortlist-объекта устарели.

### normal

Плановое обновление базы.

### low

Необязательная второстепенная характеристика.

# 27. Статусы выполнения задачи

- `success`
- `partial`
- `failed`
- `blocked`
- `captcha`
- `auth_required`
- `source_changed`
- `manual_review_required`

---

# 28. Partial — нормальный результат

Если OpenClaw нашёл:

- цену;
- площадь;
- этаж;

но не смог подтвердить:

- ПВ;

результат должен быть:

```text
partial
```

а не:

```text
failed
```

Система обновляет найденные поля и сохраняет unknown для остальных.

---

# 29. CAPTCHA / Anti-bot

Если источник блокирует автоматический доступ:

OpenClaw должен:

1. остановить агрессивные повторные запросы;
2. пометить источник;
3. вернуть `blocked / captcha`;
4. не пытаться обходить ограничения скрытым способом;
5. перевести задачу в альтернативный канал.

Например:

- API;
- feed;
- партнёрский доступ;
- ручная проверка;
- другой допустимый источник.

---

# 30. Изменение структуры сайта

Если parser больше не находит ожидаемые поля:

```text
source_changed
```

Вместо молчаливого заполнения null.

Это сигнал:

> источник требует адаптации.

---

# 31. Parser / Agent Versioning

Каждый результат должен содержать:

- agent version;
- parser version;
- schema version.

Пример:

```yaml
agent_version: openclaw-v1
parser_version: developer-x-v3
schema_version: collection-result-v1
```

Так можно выявлять ошибки после изменения parser.

---

# 32. Retry Policy

Нельзя бесконечно повторять задачу.

Для MVP:

- ограниченное количество retry;
- exponential backoff;
- различать network error и semantic error;
- не retry CAPTCHA бесконечно.

После лимита:

```text
manual_review_required
```

---

# 33. Idempotency

Повторный запуск одной задачи не должен создавать новые физические объекты без необходимости.

До записи:

1. normalization;
2. identity;
3. deduplication.

OpenClaw возвращает evidence, а база решает, обновлять ли сущность.

---

# 34. OpenClaw не пишет напрямую в canonical database

Предпочтительная архитектура:

```text
OpenClaw
   ↓
Raw/Staging Layer
   ↓
Validation
   ↓
Normalization
   ↓
Source/Evidence
   ↓
Canonical DB
```

Это снижает риск загрязнения базы ошибками агента.

---

# 35. Staging Layer

В staging сохраняем:

- raw result;
- source;
- timestamp;
- task;
- warnings;
- extraction confidence.

После этого данные проходят обработку.

---

# 36. Validation

До нормализации проверяем:

- типы;
- обязательные поля;
- диапазоны;
- currency;
- URL;
- timestamp;
- malformed values.

Пример:

```text
площадь = 4180 м²
```

для однокомнатной квартиры может быть anomaly.

Она не должна автоматически попадать в canonical database.

---

# 37. Anomaly Flags

OpenClaw / validator может ставить:

- `price_outlier`
- `area_outlier`
- `missing_identity`
- `unexpected_currency`
- `invalid_date`
- `possible_template`
- `possible_advertising_price`
- `conflicting_page_content`

Флаг не означает автоматическую ошибку, но требует обработки.

---

# 38. Template vs Concrete Unit

OpenClaw должен различать, если возможно:

```text
Конкретная квартира
```

и:

```text
типовая планировка / квартиры от ...
```

Если unit не идентифицирован:

```yaml
entity_type: inventory_template
```

а не concrete property.

---

# 39. Discovery

OpenClaw может находить список объектов.

Пример:

```text
страница ЖК
→ 120 квартир
```

Результат discovery:

- external IDs;
- URLs;
- basic identity;
- pagination info.

После discovery создаются отдельные collect tasks.

---

# 40. Не смешивать discovery и deep collection

Для масштабирования:

```text
Discovery
→ список URL/ID
→ очередь
→ deep collection
```

Это управляемее, чем один гигантский browser session.

---

# 41. Source Coverage

Для каждого источника нужно хранить:

- какие типы недвижимости покрывает;
- какие города;
- какие поля;
- насколько часто обновляется;
- насколько успешно работает агент.

Это относится к `sources.md`, но OpenClaw должен использовать этот registry.

---

# 42. Нет гарантии «все сайты»

Продукт не должен обещать буквально:

> мы обходим любой сайт в интернете.

Корректнее:

> поиск ведётся по подключённым источникам, а пользователь может добавить собственную ссылку.

OpenClaw расширяет покрытие, но не превращает технически и юридически недоступный источник в гарантированный.

---

# 43. Legal / Access Boundary

Перед массовым подключением источника необходимо определить:

- допустим ли автоматический сбор;
- существует ли API / feed;
- есть ли партнёрский вариант;
- какие ограничения существуют;
- можно ли хранить и отображать данные;
- как ссылаться на источник.

OpenClaw не должен использоваться как способ игнорировать правила источника.

---

# 44. Human-in-the-loop

OpenClaw должен уметь передавать сложный случай человеку.

Примеры:

- CAPTCHA;
- противоречивые условия акции;
- сложный PDF;
- неоднозначная квартира;
- невозможно определить объект;
- юридически значимое условие;
- банк требует звонка / персональной консультации.

Результат:

```text
manual_review_required
```

---

# 45. Expert Verification

Эксперт может выполнить:

- звонок;
- письменный запрос;
- проверку документа;
- ручную проверку сайта;
- проверку конкретной акции.

После этого создаётся manual evidence.

OpenClaw не заменяет экспертный слой.

---

# 46. Observability

Для каждого источника:

- success rate;
- average duration;
- errors;
- CAPTCHA frequency;
- fields missing;
- source_changed incidents;
- cost per run;
- last success.

На MVP достаточно базового logging.

---

# 47. Cost Control

OpenClaw/browser agent — более дорогой способ, чем API / fetch.

Поэтому:

1. кэшируем результаты;
2. используем scheduled collection;
3. обновляем только динамические поля;
4. не запускаем одинаковые задачи параллельно;
5. приоритетно используем structured source;
6. batch tasks, где это возможно.

---

# 48. Freshness-aware Collection

Data Quality Layer должен решать, что нужно обновить.

Пример:

```text
Площадь — confirmed, static
→ не обновлять.

Цена — 4 дня
→ refresh.

ПВ — claimed
→ verify.

Наличие — 2 дня
→ critical refresh.
```

---

# 49. User Waiting Strategy

Если targeted refresh занимает время:

интерфейс не должен блокировать весь результат.

Можно показать:

> По последней проверке объект подходит на 89%.  
> Обновляем цену и условия ипотеки.

После обновления Match Result пересчитывается.

---

# 50. Real-time Result Update

Pipeline:

```text
старый MatchResult
     ↓
OpenClaw refresh
     ↓
новое evidence
     ↓
canonical update
     ↓
matching recalculation
     ↓
UI update
```

---

# 51. OpenClaw и LLM

OpenClaw может использовать языковую модель внутри своих действий, но продуктовая архитектура не должна зависеть от «свободного рассуждения» агента.

Structured contracts остаются обязательными.

На выходе:

```text
не эссе
```

а:

```text
structured fields + evidence + warnings
```

---

# 52. Security

OpenClaw не должен получать:

- пользовательские пароли к банкам;
- банковские кабинеты;
- Госуслуги;
- платёжные данные;
- лишние персональные данные.

Если в будущем необходим auth connector, он проектируется отдельно.

---

# 53. User Data Minimization

При поиске недвижимости OpenClaw обычно не нужен полный профиль пользователя.

Он получает техническое задание:

> найти объекты / обновить данные.

Matching выполняется внутри продукта.

Это снижает передачу персональной информации внешним системам.

---

# 54. MVP Source Set

На первом этапе рекомендуется тестировать не «весь рынок», а репрезентативный набор:

- 3–5 сайтов застройщиков;
- несколько проектов;
- 1–2 внешних площадки, если допустимо;
- официальный/банковский финансовый источник;
- пользовательские URL;
- один источник домов / вторички.

Цель — доказать pipeline на разных структурах.

---

# 55. Proof of Concept для каждого источника

Для каждого пилотного источника проверяем:

1. discovery;
2. concrete unit extraction;
3. price extraction;
4. availability;
5. source evidence;
6. refresh;
7. source change handling;
8. deduplication inputs;
9. financing link if present.

---

# 56. MVP Acceptance Criteria для OpenClaw Layer

Слой считается работающим, если система умеет:

1. собрать конкретную квартиру с сайта застройщика;
2. сохранить URL и evidence;
3. обновить цену;
4. определить изменение цены;
5. обновить наличие;
6. собрать акцию отдельно;
7. не считать общую акцию применимой автоматически;
8. разобрать пользовательскую ссылку;
9. вернуть partial result;
10. обработать missing fields;
11. корректно сообщить CAPTCHA;
12. корректно сообщить source_changed;
13. передать запись в normalization;
14. предоставить данные для deduplication;
15. не записывать raw output напрямую в canonical DB;
16. инициировать targeted refresh;
17. хранить run log;
18. поддерживать versioning;
19. не принимать matching-решения;
20. не выдавать claimed как confirmed.

---

# 57. Что входит в MVP v1

Обязательно:

- CollectionTask;
- scheduled collection;
- targeted refresh;
- user URL ingestion;
- limited search fallback;
- structured output;
- evidence;
- extraction confidence;
- staging;
- validation;
- normalization handoff;
- source IDs;
- dynamic-field refresh;
- statuses success / partial / blocked / source_changed;
- retry policy;
- logs;
- parser versioning;
- human review handoff.

---

# 58. Что можно отложить

На потом:

- сотни параллельных источников;
- полностью автономное browser farm;
- сложный distributed scheduler;
- ML parser generation;

- пользовательские персональные банковские интеграции.

---

# 59. Рекомендуемая структура кода в будущем

Документ не требует сейчас писать код, но coding-agent должен ориентироваться на разделение:

```text
src/
  data-collection/
    tasks/
    adapters/
    openclaw/
    validators/
    staging/
    refresh/
    monitoring/
```

и не смешивать collection с matching.

---

# 60. Главный принцип для coding-agent

Нельзя строить:

```text
OpenClaw → готовая карточка пользователю
```

Правильно:

```text
OpenClaw
   ↓
Raw Result
   ↓
Validation
   ↓
Normalization
   ↓
Source Evidence
   ↓
Deduplication
   ↓
Canonical Data
   ↓
Matching
   ↓
Explanation
```

OpenClaw — **разведчик и сборщик данных**, а не арбитр.

Главное правило:

> Агент имеет право сказать «не нашёл», «не подтверждено», «данные расходятся» или «требуется ручная проверка». Он не имеет права заполнять пробелы догадкой ради красивого результата.
