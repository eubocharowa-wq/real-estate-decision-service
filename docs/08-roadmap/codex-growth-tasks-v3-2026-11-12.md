**Дата:** 12.11.2026; **статус:** техническое приложение к маркетинговой стратегии v3.0.

**Правило выполнения:** сначала один документационный PR, затем каждый SEC/MKT task отдельным PR с тестами, без автоматического слияния и без публикации персональных данных. Ничего из списка не означает разрешение включить небезопасную публичную форму.

**Основной документ:** `docs/08-roadmap/marketing-commercial-launch-v3-2026-11-12.md`.

# 14. Задания Codex / Claude Code: продукт, маркетинг, сайт

**Общая команда разработчику:** прочитать `PROJECT.md`, документы маркетинговой стратегии v3, `docs/07-expert-services/*`, `docs/09-pilot/*`, текущие issue/PR. Работать малыми PR без авто-merge; одна цель — один PR; проверять CI; **не изменять matching, Property/Offer, статусы evidence, `unknown != false`, source access policies или production DB**. Никаких новых реальных данных и секретов в PR. Обнаружив конфликт спецификации и кода, оформить вопрос в PR, не переписывать silently.

### MKT-00 — фиксация стратегии и бренда (docs-only, немедленно)

**Вход:** данный документ.  
**Файлы:** `PROJECT.md` §3/§22 (минимальные правки), новая стратегия, существующие планы v2/90 дней (пометить приоритет v3 в маркетинге), `README.md` при необходимости только бренд.  
**Результат:** одно публичное имя, архитектура «технология + эксперт», Тула как пилот, два равноправных входа.  
**Приёмка:** нет обещаний полной базы/одобрения; никаких изменений runtime и API; отдельный docs PR или поправка к существующему draft.

### SEC-01 — закрытие server-side fail-closed privacy guard (P0)

**Задача:** issue #29: на серверной границе buyer journeys, expert и upload отклонять запрос до любой записи при запрещённом режиме; controlled QA остаётся с синтетическими данными.  
**Приёмка:** интеграционные тесты forbidden/allowed, отсутствие echo сырого пользовательского текста, нет изменений секрета/production без операторского допуска; отдельный PR.

### SEC-02 — карта обработки и законность данных (P0)

**Задача:** issue #27 / PR #28 / TASK-028/TASK-031B: установить фактический регион всех узлов, ingress, PostgreSQL, объектное хранение, логи, backups, сторонние AI/метрики, путь миграции и допуск владельца как оператора ПДн.  
**Приёмка:** доказанный регион без выдачи secret, юридическое решение оператора, release gate не открыт фиктивно; отдельные PR/документы.

### MKT-01 — коммерческая архитектура главной (после SEC-01)

**Задача:** заменить абстрактное объяснение сайта на клиентскую задачу; 3 CTA; бесплатное/платное раздельно; доверие и прозрачный охват.  
**Приёмка:** доступность с клавиатуры/mobile, единственный H1, ясный путь к услуге без каталога, никаких фиктивных источников, нет ссылок на неработающие формы. В demo-контуре CTA только на безопасный информационный путь.

### MKT-02 — проверка объекта: коммерческая посадочная

**Задача:** `/property-check`: ситуация, результат, состав/исключения, цена и сроки E0/A1 по централизованному конфигу, реальный образец результата, FAQ, корректный CTA.  
**Приёмка:** структурированные ограничения, нет обещаний полной юридической проверки E0, ни одного placeholder, privacy gate не нарушается, сквозные тесты навигации.

### MKT-03 — ипотека и сложные сделки

**Задача:** `/mortgage/complex`, `/complex-transactions`, при готовности `/mortgage` и `/transaction-support`. Содержательная развилка «разобрать условия / подготовить план / сопровождать».  
**Приёмка:** «решение принимает банк», нет гарантий, юридически согласованные формулировки программ, CTA и цена не противоречат коммерческому конфигу.

### MKT-04 — экспертная страница, существующий маршрут

**Задача:** завершить `/expert-review` без `{{ТРЕБУЕТСЯ ТЕКСТ}}`; два основных маршрута жилья и инвестиционного объекта + сложная ипотека/сделка; E0/A1/S1/A2; состав, исключения, предоплата, источник вознаграждения.  
**Приёмка:** не отправлять жилой объект автоматически в A2; не требовать предварительно пройти подбор; metadata index — лишь после юридической/технической готовности.

### MKT-05 — доказательства экспертизы и ребрендинг

**Задача:** `/about`, header/footer, descriptions, карточки услуг — перейти к имени «Центр ипотеки и недвижимости „Основание“» с коротким «Основание»; убрать смешение с публичным ЦБИ.  
**Приёмка:** нет вымышленных наград, лицензий, офисов, партнёров, отзывов или товарных знаков; инвестиционный стиль при необходимости остаётся внутри `data-contour="invest"`, но не второй бренд.

### MKT-06 — SEO infra и индексация

**Задача:** аудит route metadata, canonical, `robots.txt`, `sitemap.xml`, уникальные meta title/description, OG, internal linking, structured data `Organization/ProfessionalService` лишь для подтверждённых данных, breadcrumbs и mobile/LCP.  
**Приёмка:** noindex demo; нет sitemap для неготовых/закрытых/пустых страниц; production index по отдельному operator-approved gate; Yandex Webmaster checklist; CI тесты.

### MKT-07 — CTA и безопасная воронка

**Задача:** user journey для прямого экспертного обращения и бесплатного подбора; цена/продукт определены на входе. Если безопасный бекенд недоступен — информационная страница с проверенными контактами и без подмены функциональности.  
**Приёмка:** не собирать ПДн через непроверенные POST и третьих лиц; пользователь ясно понимает следующий шаг, тесты disabled/demo/legal.

### MKT-08 — аналитика и ручная атрибуция

**Задача:** privacy-aware events без полей с PII, UTM-параметры (отобранные источники), документация ручного реестра и показателей `qualified`, `paid`, `hours`, `CAC`, `margin`.  
**Приёмка:** no raw queries/phones/passports in events/logs, разрешение на метрики до активации, e2e test/QA с синтетическими данными, платёж подтверждается вне браузера.

### MKT-09 — SEO-контент и ЖК Тулы

**Задача:** шаблон качественной страницы ЖК, источники/дата обновления/unknown и права публикации; локальные кластеры, автор, обновления, внутренняя перелинковка.  
**Приёмка:** не генерировать сотни тонких страниц без независимой ценности; noindex синтетические/неполные карточки; не объявлять интеграции законными без source policy.

### MKT-10 — контент-операции без автоматического спама

**Задача:** реестр редакционного календаря, шаблоны VK/TG/клип, UTM для согласованных ссылок, источник проверки каждого факта. Авто-публикацию не внедрять без отдельно согласованных прав, интеграций и условий площадок.  
**Приёмка:** нет автоматической рассылки клиентам; no leaked PII; работает ручной экспорт календаря.

### MKT-11 — после 5–10 оплаченных кейсов: стандартизация исполнения

**Задача:** шаблоны E0/A1/S1/A2, роли специалиста/контролёра, исходные данные, дата источника, versioning, акт/сдача.  
**Приёмка:** эксперт подтверждает вывод, AI не источник фактов, защищённые документы/аудит, без автоматического «юридически чисто».

### MKT-12 — только после прибыльных рекламных тестов: масштаб

**Задача:** варианты главной и посадочных, каналы с известным CAC, отложенная автоматизация повторяющихся операций; не менять ranking ради платных интересов.  
**Приёмка:** есть платёжная и себестоимостная статистика, ROI/вклад сравнивается по услугам; эксперимент честен и обратим.

**Очередность:** `MKT-00 (docs)` параллельно `SEC-01` → `SEC-02` + юридическая приёмка → `MKT-01/02/03/04/05` → `MKT-06/07/08` → `MKT-09/10` → `MKT-11/12`. Уточнения рынка и ручные продажи начинаются раньше технического релиза, но **не в обход законной работы с ПДн**.
