# Matching Logic — MVP v1

## 1. Назначение документа

Этот документ описывает, как сервис сопоставляет подтверждённый пользовательский запрос (`UserRequest`) с нормализованным объектом недвижимости (`PropertyCandidate`) и формирует персональный результат:

- проходит ли объект обязательные условия;
- насколько он соответствует желательным условиям;
- где есть компромиссы;
- какие критичные данные неизвестны;
- насколько надёжны исходные данные;
- почему объект получил конкретный процент соответствия;
- почему один объект оказался выше другого.

Главный принцип:

> Процент соответствия — это не оценка качества недвижимости и не универсальный рейтинг объекта. Это мера того, насколько конкретный объект соответствует конкретной задаче конкретного пользователя.

Один и тот же объект может иметь:

- 92% для одной семьи;
- 61% для другого покупателя;
- 35% для инвестора;
- быть полностью исключённым для пользователя с другим обязательным условием.

---

# 2. Что Matching Engine НЕ делает

Matching Engine не должен:

- определять, какой объект «лучший вообще»;
- заменять пользовательские требования своими предпочтениями;
- повышать рейтинг объекта из-за рекламы или комиссии;
- считать неизвестное значение выполненным условием;
- считать неизвестное значение автоматически нарушенным условием;
- игнорировать обязательный критерий ради высокого общего балла;
- скрывать недостаток данных;
- использовать LLM как единственный механизм ранжирования;
- смешивать соответствие требованиям и надёжность данных в один непрозрачный процент;
- менять подтверждённые пользователем условия без его согласия.

# 4. Основной результат Matching Engine

Для каждой пары:

```text
UserRequest × PropertyCandidate
```

система формирует:

```yaml
match_result:
  eligibility_status:
  match_score:
  data_confidence_score:
  criteria_results:
  hard_failures:
  compromises:
  unknown_critical:
  strengths:
  explanations:
  recommended_actions:
```

---

# 5. Два разных показателя

Для MVP принципиально разделяем:

## 5.1. Match Score

**Насколько объект подходит пользователю.**

Пример:

> 91% соответствует вашим условиям

## 5.2. Data Confidence

**Насколько достаточно и надёжно подтверждены данные, на которых построена оценка.**

Пример:

> Надёжность данных: 74%

Это разные показатели.

Объект может иметь:

```text
Match Score: 94%
Data Confidence: 58%
```

Это означает:

> По известным данным объект очень хорошо подходит, но для уверенного решения нужно подтвердить часть важных условий.

---

# 6. Третий технический показатель — Data Completeness

Внутри системы желательно также хранить:

`data_completeness_score`

Он отвечает на вопрос:

> Какую долю необходимых для данного запроса данных мы вообще имеем?

Пример:

- пользователь не интересуется школой → отсутствие данных о школе не ухудшает completeness для этого запроса;
- пользователь считает школу обязательной → отсутствие расстояния до школы резко снижает полноту данных.

То есть полнота должна рассчитываться **в контексте конкретного запроса**, а не только как универсальная заполненность карточки.

---

# 7. Основная последовательность matching

```text
1. Проверка данных
        ↓
2. Проверка стоп-факторов
        ↓
3. Проверка обязательных условий
        ↓
4. Проверка финансовой применимости
        ↓
5. Оценка желательных критериев
        ↓
6. Учёт пользовательских приоритетов
        ↓
7. Формирование Match Score
        ↓
8. Расчёт Data Confidence
        ↓
9. Формирование компромиссов и unknowns
        ↓
10. Объяснение результата
        ↓
11. Ранжирование shortlist
```

---

# 8. Eligibility Status — допускается ли объект в shortlist

До расчёта процентов объект получает статус.

Допустимые значения:

- `eligible`
- `eligible_with_unknowns`
- `possible_match`
- `hard_fail`
- `insufficient_data`
- `unavailable`

## eligible

Все обязательные критерии выполнены и критические данные достаточно подтверждены.

## eligible_with_unknowns

Обязательные условия по известным данным выполнены, но есть неизвестные поля, которые нужно подтвердить.

## possible_match

Есть потенциальное соответствие, но слишком много критически важных неопределённостей.

## hard_fail

Нарушено хотя бы одно подтверждённое обязательное условие.

## insufficient_data

Нельзя даже предварительно оценить ключевые требования.

## unavailable

Объект недоступен / продан / снят с продажи.

---

# 9. Hard Criteria — обязательные критерии

Критерий `priority = must` работает как gate.

Пример:

```yaml
field: purchase_price_max
operator: <=
value: 5000000
priority: must
```

Если:

```text
цена = 5 200 000
статус цены = confirmed
```

результат:

```text
hard_fail
```

Объект не должен попасть в основной shortlist как подходящий.

Даже если он идеально совпадает по:

- району;
- площади;
- школе;
- ремонту;
- этажу.

---

# 10. Unknown Hard Criteria

Если обязательный критерий не может быть проверен из-за отсутствия данных:

Пример:

```text
Пользователь:
семейная ипотека — обязательно

Объект:
family_mortgage = unknown
```

Нельзя ставить:

```text
hard_fail
```

и нельзя ставить:

```text
passed
```

Правильно:

```text
status = unknown_critical
eligibility = eligible_with_unknowns / possible_match
```

Интерфейс:

> Семейная ипотека для этого объекта пока не подтверждена.

---

# 11. Stop / Exclude Criteria

`exclude` жёстче обычного preferred/avoid.

Пример:

> «Первый этаж вообще не рассматриваю».

Если объект:

```text
floor = 1
confirmed
```

→ исключается.

Пример:

> «Только не Пролетарский район».

Если объект находится там:

→ исключается.

---

# 12. Avoid Criteria

`avoid` — сильный отрицательный фактор, но не всегда исключение.

Пример:

> «Очень не хочу первый этаж, но если вариант исключительный — покажите».

Тогда:

```yaml
priority: avoid
```

Объект может попасть в shortlist, но получает значительный penalty и явный компромисс.

---

# 13. Preferred Criteria — желательные условия

`preferred` влияют на Match Score.

Пример:

- отделка;
- парк рядом;
- большая кухня;
- балкон;
- тихий район;
- метро / остановка;
- школа;
- парковка.

Для каждого preferred-критерия рассчитывается:

`criterion_fit` от 0 до 1.

Пример:

```text
1.0  — полностью соответствует
0.8  — почти полностью
0.5  — частично
0.2  — слабое соответствие
0.0  — не соответствует
```

---

# 14. Почему нельзя использовать только 0/1

Многие критерии непрерывные.

Пример:

Пользователь:

> школа максимум 15 минут пешком

Объекты:

```text
A — 7 минут
B — 14 минут
C — 17 минут
D — 35 минут
```

Если критерий preferred, полезнее использовать плавную функцию соответствия, а не:

```text
<=15 → 1
>15 → 0
```

Пограничный объект в 17 минут может быть вполне приемлемым, если пользователь не назвал 15 минут жёстким максимумом.

---

# 15. Hard Boundary vs Preference Curve

Разница:

## Hard

> «Не больше 15 минут пешком».

```text
16 минут → hard_fail
```

## Preferred

> «Хотелось бы школу минут в 15 пешком».

```text
10 минут → 1.0
15 минут → 1.0
20 минут → 0.7
30 минут → 0.3
```

Конкретные кривые должны настраиваться по типу критерия.

---

# 16. Criterion Weight — вес критерия

Каждому preferred-критерию назначается вес.

Первичный источник веса — **сам пользователь**.

Не модель.

Базовая шкала MVP:

```text
1 — низкая важность
2 — обычная
3 — высокая
4 — очень высокая
5 — почти обязательная
```

В интерфейсе необязательно показывать цифры.

Пользователь может видеть:

- не важно;
- желательно;
- важно;
- очень важно;
- обязательно.

---

# 17. Как определить вес из естественной речи

Пример:

> «Было бы хорошо с балконом».

→ preferred, низкий/обычный вес.

> «Школа очень важна».

→ preferred, высокий вес либо запрос на уточнение, не является ли это must.

> «Мне принципиально не больше 15 минут до школы».

→ must.

LLM может предложить интерпретацию, но пользователь должен иметь возможность её исправить на экране подтверждения запроса.

---

# 18. Базовая формула Soft Match Score

После прохождения hard filters:

```text
Soft Score =
Σ(weight_i × criterion_fit_i)
────────────────────────────
Σ(weight_i for evaluable criteria)
```

Результат переводится в 0–100.

Пример:

```text
Цена по желанию       вес 5 × 1.00 = 5.00
Школа                 вес 4 × 0.90 = 3.60
Отделка               вес 3 × 0.00 = 0.00
Площадь               вес 4 × 1.00 = 4.00
Парк                   вес 2 × 0.80 = 1.60
```

Итого:

```text
14.2 / 18 = 78.9%
```

Это базовая концепция, а не окончательная формула production-системы.

---

# 19. Must Criteria и процент

Важный принцип:

Обязательные критерии не должны просто становиться очень большим весом.

Они работают **до** рейтинга.

Правильно:

```text
must → gate
preferred → score
avoid → penalty / compromise
unknown → uncertainty
```

Неправильно:

```text
все критерии складываем в одну сумму
```

Иначе объект может математически компенсировать нарушение обязательного бюджета красивым видом и большой площадью.

---

# 20. Когда все требования обязательные

Если пользователь задал только must-критерии и объект их все выполняет, нельзя автоматически всем объектам ставить 100%.

В этом случае shortlist можно ранжировать дополнительными параметрами:

- запас относительно ограничений;
- цена;
- полнота данных;
- свежесть;
- количество неподтверждённых условий;
- дополнительные пожелания, если пользователь их указал;
- diversity ranking.

Но пользовательский процент должен оставаться объяснимым.

---

# 21. Margin — запас относительно границы

Даже для выполняемого критерия полезно считать margin.

Пример:

Бюджет:

```text
максимум 5 000 000
A = 4 200 000
B = 4 990 000
```

Оба проходят must.

Но A имеет:

> запас 800 000 ₽

B:

> почти на верхней границе бюджета.

Это не должно автоматически означать, что A лучше — у B могут быть другие преимущества.

Но margin используется в объяснениях и некоторых tie-breakers.

---

# 22. Финансовый matching

Финансовые критерии должны оцениваться на уровне `PurchaseScenario`, а не только объекта.

Пример:

Одна квартира:

```text
Scenario A:
ПВ 1 млн
платёж 55 тыс.

Scenario B:
ПВ 0
платёж 72 тыс.

Scenario C:
рассрочка
ПВ 300 тыс.
финальный платёж через год
```

Для пользователя:

```text
ПВ = 0 — must
платёж <= 80 тыс. — must
```

подходит Scenario B.

Значит объект может быть подходящим, несмотря на то что стандартная ипотека не соответствует.

---

# 23. Property Match vs Purchase Scenario Match

Рекомендуется разделять:

`property_fit`

и

`purchase_scenario_fit`

Например:

```text
Квартира как жильё: 94%
Финансовый сценарий: 71%
Итоговое соответствие: 84%
```

В MVP пользователю можно показывать один итоговый Match Score, но внутренне эти компоненты лучше хранить отдельно.

---

# 24. Goal-specific Matching

Одинаковые поля имеют разный смысл в зависимости от цели.

## Для собственного проживания

Сильнее могут влиять:

- срок въезда;
- инфраструктура;
- школа;
- транспорт;
- ремонт;
- планировка;
- ежемесячная нагрузка.

## Для переезда

Дополнительно:

- город;
- рынок;
- климат/региональные условия в будущем;
- доступность работы;
- сроки;
- инфраструктура.

## Для инвестиции

В будущем:

- доходность;
- ликвидность;
- аренда;
- спрос;
- рост стоимости.

В MVP нельзя автоматически применять инвестиционные веса к пользователю, который покупает для жизни.

---

# 25. Cross-type Matching — сравнение разных типов

Чтобы сравнить:

- новостройку;
- вторичку;
- дом;

часть критериев должна приводиться к общим метрикам.

Общие измерения:

- полная стоимость входа;
- ежемесячная нагрузка;
- срок въезда;
- площадь;
- комнаты;
- готовность к проживанию;
- ремонт;
- транспорт;
- школа;
- другие user-specific POI;
- неопределённость;
- данные и риски.

Типоспецифические поля не должны искусственно давать преимущество одному типу.

Например:

> отсутствие лифта

не является проблемой для одноэтажного дома.

---

# 26. Normalized Criterion Interface

Каждый criterion evaluator должен возвращать единый формат:

```yaml
criterion_id:
field:
priority:
weight:
status:
fit:
actual_value:
target_value:
difference:
verification_status:
confidence:
explanation:
```

Пример:

```yaml
criterion_id: school_walk_time
field: school_walk_time_min
priority: preferred
weight: 4
status: matched
fit: 0.9
actual_value: 12
target_value: 10
difference: 2
verification_status: confirmed
confidence: high
explanation: "До школы около 12 минут пешком."
```

---

# 27. Criterion Status

Возможные значения:

- `matched`
- `partially_matched`
- `not_matched`
- `unknown`
- `conflicting`
- `not_applicable`
- `hard_failed`

---

# 28. Not Applicable

Не каждый критерий применим ко всем объектам.

Пример:

Пользователь сравнивает дом и квартиру.

Поле:

`floor`

для дома может быть `not_applicable`, если смысл критерия был «не первый этаж в многоквартирном доме».

`not_applicable` не должен давать 0.

Он исключается из знаменателя soft score.

---

# 29. Unknown Data и Score

Неизвестные данные нельзя считать:

```text
fit = 0
```

Иначе мы будем наказывать объект за отсутствие данных так же, как за реальное несоответствие.

Но неизвестность нельзя игнорировать полностью.

Поэтому:

- Match Score рассчитывается по доступным evaluable criteria;
- Data Confidence снижается;
- пользователь видит unknown;
- если unknown относится к must → eligibility меняется.

---

# 30. Conflicting Data

Если источники расходятся:

```text
школа: 8 минут / 17 минут
```

или:

```text
ПВ 0 / минимум 20%
```

критерий получает:

`status = conflicting`

и снижает Data Confidence.

Для критического must:

→ `eligible_with_unknowns` / `possible_match`.

---

# 31. Data Confidence Score

Внутренне Data Confidence можно считать по критериям, важным именно этому пользователю.

Примерная модель:

```text
confirmed    → 1.00
claimed      → 0.70
unconfirmed  → 0.45
conflicting  → 0.25
stale        → 0.25–0.50
unknown      → 0.00
```

Дальше:

```text
Data Confidence =
Σ(importance_i × data_confidence_i)
──────────────────────────────────
Σ(importance_i)
```

Конкретные коэффициенты позднее калибруются тестами.

---

# 32. Не смешивать Match и Data Confidence

Неправильно:

```text
Match Score = soft fit × source confidence
```

без объяснения.

Пользователь не поймёт:

> объект подходит плохо или мы просто мало о нём знаем?

Поэтому показываем отдельно:

```text
Соответствие: 91%
Надёжность данных: средняя
```

А в сортировке можем аккуратно учитывать оба параметра.

---

# 33. Ranking Score — технический показатель сортировки

Внутри системы можно иметь отдельный:

`ranking_score`

Он нужен только для порядка shortlist.

Он может учитывать:

- match score;
- eligibility;
- data confidence;
- freshness;
- количество critical unknowns;
- пользовательские приоритеты;
- diversity.

Этот score не обязательно показывать пользователю.

---

# 34. Почему лучший Match Score не всегда должен быть первым

Пример:

A:
```text
Match 95%
Confidence 42%
```

B:
```text
Match 92%
Confidence 94%
```

Для shortlist B может быть разумно поставить выше.

Но интерфейс должен показывать реальные показатели, а не менять проценты.

---

# 35. Diversity Ranking

Если первые 5 мест занимают пять почти одинаковых квартир одного ЖК, shortlist может быть бесполезным.

В MVP можно применять мягкую диверсификацию:

- не заполнять весь shortlist одним ЖК, если есть близкие альтернативы;
- показывать разные типы объекта, если пользователь разрешил;
- показывать разные разумные сценарии решения.

Но diversity не должна вытеснять значительно более подходящий объект.

---

# 36. Search vs Shortlist

Matching Engine сначала оценивает **всех кандидатов**, доступных из подключённых источников.

Потом формирует shortlist.

Пример:

```text
Найдено 186
Hard filters прошли 37
Полноценно оценены 31
Shortlist = 7
```

Пользователь не должен получать «первые пять найденных OpenClaw».

---

# 37. Match Score Bands

Для UX можно использовать диапазоны.

Примерная семантика:

```text
90–100 → очень высокое соответствие
80–89  → высокое
70–79  → хорошее, есть компромиссы
60–69  → частичное
<60    → обычно не входит в основной shortlist
```

Но диапазоны не должны использоваться как универсальные оценки качества недвижимости.

---

# 38. Compromises — компромиссы

Компромисс формируется, когда:

- preferred-критерий не выполнен;
- avoid-критерий присутствует;
- объект находится близко к жёсткой границе;
- финансовая схема хуже желаемой;
- один сценарий выигрывает по одному параметру и проигрывает по другому.

Пример:

> Вы хотели готовую отделку, но квартира передаётся в предчистовом состоянии.

> Объект укладывается в бюджет, но ежемесячный платёж почти достигает вашего максимума.

---

# 39. Strengths — почему подходит

Strength формируется только из критериев пользователя.

Не из рекламных достоинств.

Плохой пример:

> Красивый фасад, современный ЖК.

Если пользователь этого не задавал — это не персональный аргумент.

Хороший пример:

> Вы хотели не более 70 тыс. ₽ в месяц — расчётный платёж около 63 тыс. ₽.

---

# 40. Unknown Critical — что нужно проверить

В отдельный список попадают:

- неизвестный must;
- claimed финансовое условие;
- conflicting data;
- stale критическое поле;
- данные, без которых решение может существенно измениться.

Пример:

> Требуется подтвердить, действует ли схема без первоначального взноса именно для этой квартиры.

---

# 41. Recommended Actions

Matching Engine может сформировать следующее полезное действие.

Например:

- проверить ипотечное условие;
- запросить актуальную цену;
- проверить документы;
- уточнить срок передачи;
- добавить свой вариант;
- сравнить два финальных объекта;
- обратиться за экспертным разбором.

Но система не должна навязывать платную услугу независимо от результата.

---

# 42. Explainability Object

Для каждого результата создаётся структурированное объяснение.

```yaml
explanation:
  headline:
  top_reasons:
  compromises:
  unknowns:
  hard_failures:
  financial_summary:
  comparison_notes:
```

LLM может превратить эту структуру в естественный текст.

Но фактическая логика должна поступать из Matching Engine.

---

# 43. Роль LLM

LLM разрешено:

- понять естественную формулировку пользователя;
- предложить нормализацию критерия;
- сформулировать понятное объяснение готового score;
- сгруппировать похожие критерии;
- задать уточняющий вопрос;
- объяснить компромисс.

LLM нельзя:

- самостоятельно назначать итоговый процент без правил;
- игнорировать hard filter;
- придумывать значение отсутствующего поля;
- повышать объект из-за «общего впечатления»;
- превращать claimed в confirmed.

---

# 44. Пример полного matching

Пользователь:

```text
Тула
до 5 млн — обязательно
семейная ипотека — обязательно
без ПВ — желательно
не первый этаж — обязательно
отделка — желательно
школа рядом — важно
```

Объект:

```text
Цена: 4.89 млн — confirmed
Семейная ипотека: claimed
ПВ 0: claimed
Этаж: 7 — confirmed
Отделка: предчистовая — confirmed
Школа: 12 минут — confirmed
```

Результат:

```yaml
eligibility_status: eligible_with_unknowns

hard:
  price: pass
  family_mortgage: unknown_critical
  floor: pass

soft:
  zero_initial_payment:
    fit: 1.0
    verification: claimed

  finishing:
    fit: 0.3

  school:
    fit: 0.9

match_score: 82
data_confidence_score: 71
```

Интерфейс:

> **82% соответствует вашим условиям**

Почему подходит:
- цена в пределах бюджета;
- 7 этаж;
- школа примерно в 12 минутах;
- заявлена схема без ПВ.

Компромисс:
- отделка не готовая.

Нужно проверить:
- применимость семейной ипотеки;
- условия схемы без первоначального взноса.

---

# 45. Пример hard fail

Пользователь:

> максимум 5 млн — строго.

Объект:

> 5,35 млн, цена confirmed.

Даже если остальные поля дают условные 98%:

```yaml
eligibility_status: hard_fail
hard_failures:
  - purchase_price_max
```

В основном shortlist не показываем.

Можно отдельно:

> Не подходит по обязательному условию. Если увеличить бюджет до 5,35 млн, этот вариант станет доступен для сравнения.

Только если пользователь согласится изменить запрос.

---

# 46. Если точных совпадений нет

Matching Engine формирует:

`constraint_pressure`

Он показывает, какие must-условия сильнее всего сокращают выбор.

Пример:

```yaml
constraint_pressure:
  - criterion: zero_initial_payment
    excluded_candidates: 18

  - criterion: purchase_price_max
    excluded_candidates: 12
```

Интерфейс:

> Точных совпадений нет. Самое сильное ограничение — нулевой первоначальный взнос.

---

# 47. Relaxation Suggestions

Система может предложить сценарии:

```text
ПВ до 300 тыс. → +7 вариантов
Бюджет до 5,3 млн → +4 варианта
Убрать обязательную отделку → +9 вариантов
```

Важно:

> система только показывает последствия изменения условий.

Она не меняет условия сама.

---

# 48. Сравнение сценариев решения

Для пользователя со сложной задачей Matching Engine может сформировать не только рейтинг объектов, но и несколько стратегий.

Например:

### Сценарий A — минимальный вход
Новостройка.

### Сценарий B — въехать сразу
Вторичная квартира.

### Сценарий C — максимальная площадь
Дом.

Это особенно важно для идеи сервиса: сравнивать не только похожие объявления, а **разные способы решить одну жизненную задачу**.

---

# 49. Goal Fit vs Object Fit

В перспективе полезно различать:

`object_fit`

и

`solution_fit`

Пример:

Дом может идеально соответствовать площади и цене, но создавать неприемлемый ежедневный маршрут.

Квартира может быть меньше, но лучше решать общую задачу семьи.

Для MVP можно использовать единый Matching Engine, но архитектура должна позволять развить уровень `solution_fit`.

---

# 50. Результат для comparison engine

При сравнении объектов Matching Engine должен возвращать по каждому:

- итоговое соответствие;
- hard status;
- top strengths;
- top compromises;
- critical unknowns;
- финансовый сценарий;
- data confidence;
- значения по общим критериям.

Это позволит создать таблицу:

```text
                 A       B       C
Соответствие     92%     86%     81%
Въезд            позже   сразу   сразу
ПВ               0?      1.2м    1.5м
Площадь          42      48      85
Школа            12мин   7мин    22мин
Данные            71%     93%     85%
```

# 52. Algorithm Versioning

Любой Match Result должен хранить:

`algorithm_version`

Причина:

Если позже изменятся:

- веса;
- curves;
- критерии;
- финансовая логика;

мы должны понимать, по какой версии был рассчитан старый результат.

---

# 53. Recalculation

Match Result пересчитывается, если меняется:

- пользовательский запрос;
- обязательность критерия;
- объект;
- цена;
- финансирование;
- наличие;
- критические данные;
- алгоритм.

Пользователь может изменить одно условие без создания запроса с нуля.

---

# 54. Personalization без «чёрного ящика»

В MVP персонализация строится на:

- явно указанных условиях;
- подтверждённых приоритетах;
- пользовательских исправлениях.

Не используем скрытое поведенческое профилирование для изменения итогового рейтинга без объяснения.

Позже поведение можно использовать как подсказку:

> «Вы часто сохраняете варианты с готовой отделкой. Сделать отделку более важным критерием?»

Но изменение только после согласия.

---

# 55. Bias / Commercial Neutrality

Matching Engine не должен учитывать:

- размер комиссии;
- партнёрский статус;
- рекламную оплату;
- коммерческую выгоду сервиса;

как фактор Match Score.

Если в будущем появляются рекламные позиции, они должны быть явно отделены от персонального ranking.

Это необходимо для сохранения доверия к УТП.

---

# 56. Тестирование matching

Минимальный benchmark должен содержать реальные пользовательские задачи.

Например:

1. до 5 млн + семейная ипотека + ПВ 0;
2. семья с двумя детьми + школа;
3. переезд без выбранного города;
4. новостройка vs вторичка;
5. дом vs квартира;
6. жёсткий срок въезда;
7. жёсткий ежемесячный платёж;
8. много preferred-критериев;
9. конфликтующие требования;
10. объект с низким data confidence.

Для каждого набора эксперт вручную отмечает:

- какие объекты должны быть исключены;
- какие должны войти в shortlist;
- причины;
- ожидаемый порядок.

---

# 57. Метрики качества matching

На MVP:

- hard-filter accuracy;
- shortlist relevance;
- top-k precision;
- explanation correctness;
- unknown detection accuracy;
- financial-condition accuracy;
- user correction rate;
- expert disagreement rate.

Особенно важно:

> система не должна пропускать нарушение обязательного критерия.

---

# 58. Human Review

Для пограничных случаев должна существовать возможность экспертного разбора.

Например:

```text
Match 89%
Confidence 48%
3 critical unknowns
```

Сервис может предложить:

> Объект выглядит подходящим, но ключевые условия стоит проверить.

Это естественный переход в экспертный слой проекта.

---

# 59. Что входит в MVP v1

Обязательно:

- hard filters;
- preferred scoring;
- avoid penalties;
- unknown handling;
- conflicting handling;
- match score;
- data confidence;
- data completeness;
- financing scenario matching;
- cross-type common metrics;
- strengths;
- compromises;
- critical unknowns;
- explanations;
- constraint pressure;

- JSON Match Result.

# 60. Что можно отложить

На потом:

- ML-рекомендации;
- learning-to-rank;
- collaborative filtering;
- поведенческая персонализация;
- автоматическое обучение weights;
- инвестиционный прогноз;

- рекомендательный граф;
- probabilistic utility models;
- A/B-trained ranking.

MVP должен быть rule-based, объяснимым и тестируемым.

---

# 61. Критерий готовности Matching Logic

Модуль считается готовым, если он корректно обрабатывает:

1. объект, выполняющий все must;
2. объект, нарушающий один must;
3. объект с неизвестным must;
4. объект с конфликтующим must;
5. несколько preferred-критериев;
6. avoid-критерий;
7. разные типы недвижимости;
8. разные финансовые сценарии одной квартиры;
9. жёсткий бюджет;
10. жёсткий ежемесячный платёж;
11. отсутствие точных совпадений;
12. предложение ослабить одно условие;
13. объект с высоким match и низким confidence;
14. объект с немного меньшим match и высоким confidence;
15. сравнение новостройки, вторички и дома.

---

# 62. Главный принцип для coding-agent

Нельзя реализовывать Matching Engine как:

```text
отправить объекты и запрос в LLM
→ попросить расставить проценты
```

Правильная архитектура:

```text
UserRequest
     ↓
Hard Criteria Gate
     ↓
Purchase Scenario Eligibility
     ↓
Criterion Evaluators
     ↓
Weighted Soft Matching
     ↓
Unknown / Conflict Analysis
     ↓
Match Score + Data Confidence
     ↓
Structured Explanation
     ↓
LLM формулирует объяснение
```

Главное правило:

> Сначала вычисляемое и проверяемое соответствие. Потом — человеческое объяснение.

Процент должен быть воспроизводимым: если запрос и данные объекта не изменились, система должна получить тот же результат независимо от того, как LLM сформулировал текст.
