# Deduplication Model — MVP v1

## 1. Назначение документа

Этот документ описывает, как сервис определяет, что несколько объявлений или предложений из разных источников относятся к одному и тому же физическому объекту недвижимости.

Типичная ситуация:

- квартира есть на сайте застройщика;
- та же квартира опубликована на классифайде;
- её разместило агентство;
- пользователь принёс ещё одну ссылку;
- цена и часть характеристик в источниках различаются.

Сервис не должен показывать это как четыре разных объекта.

Главный принцип:

> Мы объединяем не страницы и не объявления, а предложения, относящиеся к одному физическому объекту. При этом исходные предложения, цены, условия и источники не теряются.

---

# 2. Что именно дедуплицируем

Необходимо различать три уровня:

## 2.1. Physical Property

Физический объект недвижимости.

Примеры:

- конкретная квартира №145 в корпусе 2;
- конкретная вторичная квартира по адресу;
- конкретный дом;
- конкретный земельный участок.

## 2.2. Offer

Предложение о продаже этого объекта.

Один физический объект может иметь несколько `Offer`:

- от застройщика;
- от собственника;
- от агентства;
- на классифайде;
- в партнёрской базе.

## 2.3. Purchase Scenario

Один Offer может иметь несколько сценариев покупки:

- обычная ипотека;
- семейная ипотека;
- рассрочка;
- акция;
- схема с другим первоначальным взносом.

Финансовые сценарии не являются дублями объекта.

Схема:

```text
Physical Property
   ├── Offer A — сайт застройщика
   │      ├── Scenario 1
   │      └── Scenario 2
   │
   ├── Offer B — классифайд
   │
   └── Offer C — агентство
```

---

# 3. Главная задача Deduplication Engine

На вход:

```text
множество нормализованных Offer
```

На выход:

```text
кластеры Offer, относящихся к одному Physical Property
```

Для каждой пары / группы система должна определить один из статусов:

- `same_property`
- `probable_same_property`
- `possible_duplicate`
- `different_property`
- `insufficient_data`
- `manual_review`

---

# 4. Почему URL и цена не являются идентификаторами

Нельзя определять объект только по URL.

Одна квартира может иметь много URL.

Нельзя определять объект только по цене.

Цена может:

- меняться;
- отличаться у застройщика и агента;
- зависеть от способа оплаты;
- включать скидку;
- быть устаревшей.

Нельзя определять объект только по телефону продавца.

Один агент может продавать сотни объектов.

Нельзя определять объект только по планировке.

В одном ЖК может быть несколько одинаковых квартир.

---

# 5. Strong Identifiers — сильные идентификаторы

Сильные признаки имеют наибольший вес.

## Для новостройки

- ID квартиры у застройщика;
- номер квартиры;
- корпус / дом;
- секция;
- этаж;
- номер на этаже;
- уникальный внешний ID из официального фида;
- кадастровый номер, если уже существует.

Комбинация:

```text
development + building + unit_number
```

может быть почти однозначным идентификатором, если данные подтверждены.

## Для вторички

- кадастровый номер;
- полный нормализованный адрес + номер квартиры;
- подтверждённый уникальный ID объекта из партнёрского источника.

## Для дома

- кадастровый номер дома;
- кадастровый номер участка;
- точный адрес;
- координаты + участок + площадь.

## Для участка

- кадастровый номер;
- точные координаты / границы;
- адрес участка.

---

# 6. Medium Identifiers — средние признаки

Используются в комбинации:

- нормализованный адрес;
- ЖК;
- корпус;
- секция;
- этаж;
- количество комнат;
- общая площадь;
- жилая площадь;
- площадь кухни;
- тип планировки;
- координаты;
- год постройки;
- площадь участка;
- материал дома.

Один средний признак не должен автоматически создавать дубль.

---

# 7. Weak Identifiers — слабые признаки

Слабые признаки используются только как дополнительное подтверждение:

- цена;
- описание;
- телефон;
- имя агента;
- заголовок;
- фотографии;
- одинаковые рекламные формулировки;
- дата публикации;
- ставка ипотеки;
- акция.

Они не могут быть основным основанием для merge.

---

# 8. Нормализация адреса

До сравнения адрес должен приводиться к стандартной форме.

Пример:

```text
г. Тула, ул. Ленина, д. 10, кв. 25
Тула, Ленина 10-25
ул Ленина д 10 квартира 25
```

должны потенциально нормализоваться к одной структуре:

```yaml
country: RU
region: Тульская область
city: Тула
street: Ленина
house_number: "10"
building_number: null
apartment_number: "25"
```

Нужно отдельно хранить:

- исходную строку;
- нормализованную структуру;
- confidence нормализации.

---

# 9. Нормализация ЖК, корпуса и секции

Названия могут отличаться:

```text
ЖК Первый
Жилой комплекс «Первый»
Первый ЖК
```

Нужно иметь canonical entity:

```yaml
development_id: development_001
canonical_name: "ЖК Первый"
aliases:
  - "Первый"
  - "Жилой комплекс Первый"
```

Корпус:

```text
корп. 2
корпус 2
дом 2
литер 2
```

не всегда означают одно и то же.

Нормализация должна учитывать словарь конкретного проекта, если он известен.

---

# 10. Площадь — допустимые расхождения

Площадь часто различается из-за:

- округления;
- балконных коэффициентов;
- проектной / фактической площади;
- ошибок площадки.

Поэтому точное равенство не требуется.

Примерный подход:

```text
41.8 м² vs 41.9 м²
```

→ сильное совпадение.

```text
41.8 м² vs 42.5 м²
```

→ возможно, но требует других подтверждений.

```text
41.8 м² vs 48.0 м²
```

→ скорее разные объекты.

Конкретные tolerances должны быть конфигурируемыми, а не жёстко зашитыми в бизнес-логику.

---

# 11. Комнаты и тип планировки

Нужно учитывать различия терминологии:

```text
евродвушка
2Е
1 спальня + кухня-гостиная
двухкомнатная евроформата
```

могут описывать один тип планировки.

Но система не должна автоматически считать:

```text
1-комнатная
```

и

```text
2-комнатная
```

одним объектом без дополнительных доказательств.

---

# 12. Этаж

Этаж — сильный вспомогательный признак.

Если:

```text
объект A: этаж 7
объект B: этаж 14
```

и нет сильного общего идентификатора,

→ это почти наверняка разные квартиры.

Но для домов и участков поле не применяется.

---

# 13. Цена

Цена используется только как слабый / средний динамический признак.

Пример:

```text
4 890 000
4 990 000
```

не исключает дубль.

Причины:

- скидка;
- разные программы;
- устаревшая публикация;
- комиссия;
- разные условия оплаты.

При merge сохраняются обе цены как значения разных Offer.

---

# 14. Фотографии

Фотографии могут помогать обнаружению дублей, особенно на вторичном рынке.

В будущем можно использовать:

- perceptual hash;
- similarity embeddings;
- совпадение набора изображений.

Но фотография не является абсолютным идентификатором.

Почему:

- один агент может использовать типовые фото;
- новостройки используют рендеры;
- одинаковая планировка может иметь одинаковые изображения;
- фото могут быть обрезаны / изменены.

Для MVP это дополнительный сигнал, не обязательное ядро.

---

# 15. Текст описания

Можно использовать similarity текста как слабый сигнал.

Например:

> одинаковый редкий текст + одинаковый адрес + одинаковая площадь

усиливает вероятность дубля.

Но копирование описаний между агентствами не должно само по себе объединять объекты.

---

# 16. Candidate Generation — поиск кандидатов на дубль

Нельзя сравнивать каждый объект со всеми объектами базы.

Сначала формируем небольшую группу кандидатов — blocking.

Примерные блоки:

### Для квартиры

```text
city
+ normalized building/address
+ approximate area
```

или:

```text
development_id
+ building_id
+ floor
```

### Для дома

```text
settlement
+ approximate coordinates
+ house_area range
```

### Для участка

```text
cadastral region
+ coordinates
+ land_area range
```

После этого запускается более точное сравнение.

---

# 17. Match Features — признаки для сравнения

Для каждой пары Offer рассчитываем признаки.

Пример:

```yaml
same_cadastral_number: true/false/null
same_developer_unit_id: true/false/null
same_address: score
same_building: score
same_unit_number: score
same_floor: score
area_similarity: score
rooms_similarity: score
coordinates_distance: value
photo_similarity: score
description_similarity: score
price_similarity: score
```

---

# 18. Deduplication Score

Вводим:

`duplicate_score`

например от 0 до 100.

Примерная логика:

### Очень сильные признаки

- одинаковый кадастровый номер;
- одинаковый подтверждённый developer unit ID;
- одинаковый адрес + квартира.

### Средние

- одинаковый корпус;
- этаж;
- площадь;
- комнаты;
- координаты.

### Слабые

- цена;
- фото;
- текст;
- продавец.

Вес должен зависеть от типа недвижимости.

---

# 19. Не использовать один общий алгоритм для всех типов

Deduplication Profile:

- `new_build_apartment`
- `secondary_apartment`
- `house`
- `townhouse`
- `land`

Пример:

Для новостройки номер квартиры у застройщика очень важен.

Для вторички он часто отсутствует в публичном объявлении.

Для дома площадь участка и координаты становятся значительно важнее.

---

# 20. Пример правил для новостройки

Если совпадают:

- ЖК;
- корпус;
- квартира №145;

→ `same_property` с высокой уверенностью.

Если номер квартиры отсутствует, но совпадают:

- ЖК;
- корпус;
- секция;
- этаж;
- площадь 41,8;
- комнаты;
- планировка;

→ `probable_same_property`.

Если совпадают только:

- ЖК;
- площадь;
- цена;

→ недостаточно данных.

В одном корпусе может быть много одинаковых квартир.

---

# 21. Пример правил для вторичной квартиры

Вариант A:

```text
Тула, ул. Ленина 10
2 комнаты
48.2 м²
5 этаж
```

Вариант B:

```text
Тула, Ленина, д.10
2-комнатная
48.0 м²
5/9
```

Если номер квартиры скрыт, нужны дополнительные признаки:

- фотографии;
- одинаковая планировка;
- текст;
- координаты;
- детали ремонта;
- дата;
- продавец.

Результат может быть:

`probable_same_property`, а не `same_property`.

---

# 22. Пример правил для дома

Совпадают:

- точный адрес;
- координаты;
- площадь дома;
- участок;
- фотографии;

→ высокая вероятность дубля.

Но два дома в одном коттеджном посёлке одинаковой площади нельзя объединять только по:

- площади;
- цене;
- фото типового проекта.

---

# 23. Пороговые статусы

Пороговые значения должны быть конфигурируемыми.

Пример логики, не финальные числовые правила:

```text
очень высокий score + сильный identifier
→ same_property

высокий score, но без сильного identifier
→ probable_same_property

средний score
→ possible_duplicate / manual_review

низкий score
→ different_property
```

Coding-agent не должен самостоятельно придумывать окончательные thresholds без отдельной задачи / тестирования.

---

# 24. Merge — объединение

Если Offer признаны относящимися к одному объекту:

создаётся / используется один `PhysicalProperty`.

Но Offer сохраняются отдельно.

Нельзя делать:

```text
Offer A + Offer B → одна строка, остальные данные потеряны
```

Правильно:

```text
PhysicalProperty P1
  ├── Offer A
  ├── Offer B
  └── Offer C
```

---

# 25. Canonical Value — какое значение показывать

Если у нескольких Offer разные данные, физический объект может иметь canonical value.

Например:

```text
площадь:
A = 41.8
B = 41.8
C = 42.0
```

Canonical value выбирается на основании:

- качества источника;
- свежести;
- конкретности;
- подтверждённости;
- конфликтов.

Но все исходные значения сохраняются.

---

# 26. Merge Policy для динамических полей

Динамические поля нельзя объединять как одно постоянное свойство.

Например:

- цена;
- акция;
- наличие;
- финансирование.

Они остаются на уровне Offer / FinancingOffer.

Так пользователь может увидеть:

> Один объект  
> 3 источника  
> Цена от 4,89 млн  
> На другом сайте — 4,99 млн

---

# 27. Merge Policy для физических полей

Физические поля обычно canonical:

- площадь;
- этаж;
- комнаты;
- адрес;
- номер квартиры;
- площадь участка.

Но при конфликте:

```text
canonical_status: conflicting
```

и нельзя молча выбрать удобное значение.

---

# 28. Evidence сохраняется

Любое решение о merge должно иметь доказательства.

`DeduplicationDecision`:

- `decision_id`
- `property_id`
- `offer_ids`
- `duplicate_score`
- `status`
- `features`
- `strong_identifiers`
- `conflicts`
- `created_at`
- `algorithm_version`
- `reviewed_by`
- `review_note`

---

# 29. Audit Trail

Нужно хранить историю:

```text
12.08 10:00 — Offer A добавлен
12.08 10:05 — Offer B найден
12.08 10:05 — score 93
12.08 10:05 — объединены как probable_same_property
12.08 12:00 — эксперт подтвердил
```

Это важно для исправления ошибок.

---

# 30. False Merge — ошибочное объединение

Система обязательно должна позволять разделить ошибочно объединённые объекты.

Операция:

`split_cluster`

После split:

- создаются отдельные PhysicalProperty;
- Offer перераспределяются;
- evidence не теряется;
- старое решение сохраняется в audit log.

---

# 31. Missed Duplicate — пропущенный дубль

Также должно быть возможно вручную:

`merge_properties`

если система не распознала дубль автоматически.

Причина сохраняется:

- эксперт подтвердил;
- пользователь сообщил;
- найден новый сильный identifier.

---

# 32. Работа с пользовательской ссылкой

Пользователь вставляет объект с Авито / ЦИАН / сайта застройщика / другого источника.

Алгоритм:

1. создать Offer;
2. нормализовать данные;
3. сформировать blocking candidates;
4. сравнить с PhysicalProperty;
5. если найден дубль — присоединить Offer;
6. если не найден — создать новый PhysicalProperty;
7. показать пользователю результат.

Например:

> Этот объект уже есть в нашей базе. Мы добавили найденный вами источник к существующему варианту.

Это полезная функция, а не ошибка.

---

# 33. Если пользовательские данные отличаются

Пример:

База:

```text
4 890 000 ₽
```

Ссылка пользователя:

```text
4 750 000 ₽
```

После обнаружения дубля система не заменяет цену.

Она показывает:

> В найденном вами источнике цена ниже на 140 000 ₽. Проверяем условия предложения.

---

# 34. OpenClaw и дедупликация

OpenClaw не должен принимать финальное решение о дубле.

Его роль:

- собрать идентификаторы;
- нормализовать доступные поля;
- вернуть внешний ID;
- вернуть адрес;
- вернуть корпус;
- вернуть квартиру;
- вернуть площадь;
- вернуть этаж;
- вернуть source URL;
- предоставить evidence.

Deduplication Engine работает после нормализации.

---

# 35. Что OpenClaw особенно должен искать

Для новостройки:

- internal property / unit ID;
- номер квартиры;
- корпус;
- секцию;
- этаж;
- планировку;
- площадь;
- URL конкретной квартиры.

Для вторички:

- полный адрес;
- координаты;
- этаж;
- площадь;
- комнаты;
- фотографии;
- уникальные характеристики.

Для дома:

- адрес;
- координаты;
- кадастровые данные, если опубликованы;
- площадь дома;
- площадь участка;
- фотографии.

---

# 36. OpenClaw не должен

- объединять записи только по одинаковому названию;
- считать одинаковую цену доказательством;
- считать одинаковые фото рендера доказательством;
- удалять «дубли» из raw data;
- перезаписывать один Offer другим;
- терять URL и evidence;
- считать квартиру и типовую планировку одним и тем же.

---

# 37. Типовая планировка vs конкретная квартира

Это отдельный важный случай.

Сайт может показывать:

```text
1-комнатная
41.8 м²
от 4,8 млн
```

без номера квартиры.

Это не PhysicalProperty конкретной квартиры.

Тип:

`InventoryTemplate` / `LayoutOffer`

Он может использоваться для информирования, но не должен объединяться с конкретной квартирой без доказательства.

---

# 38. Один объект с разными условиями покупки

Пример:

Квартира №145:

- 4,89 млн при 100% оплате;
- 5,2 млн при субсидированной ипотеке;
- другая цена при рассрочке.

Это НЕ три PhysicalProperty.

Это:

```text
PhysicalProperty #145
   ↓
Offer / Purchase Scenarios
```

Дедупликация должна это сохранять.

# 39. Один адрес — несколько квартир

Особенно для вторички.

```text

48 м²
2 комнаты
```

может относиться к нескольким квартирам.

Нужны:

- этаж;
- квартира;

`possible_duplicate`

а не автоматический merge.

# 44. Качество дедупликации

Нужно отслеживать минимум два типа ошибок:

## False Positive

Разные объекты ошибочно объединены.

Это особенно опасно.

## False Negative

Один объект остался в системе как несколько разных.

Для пользовательского продукта false positive обычно хуже false negative.

Поэтому система должна быть консервативной:

> лучше временно показать возможный дубль, чем объединить две разные квартиры.

---

# 45. Метрики качества

Для тестирования:

- precision merge;
- recall duplicate detection;
- false merge rate;
- manual review rate;
- unresolved duplicate rate.

Для MVP приоритет:

**минимизировать false merge.**

---

# 46. Тестовый набор

Перед запуском нужно собрать ручной benchmark.

Минимум:

- 20 подтверждённых дублей новостроек;
- 20 разных квартир одного ЖК;
- 20 дублей вторички;
- 20 похожих, но разных вторичных квартир;
- 10 дублей домов;
- 10 похожих домов одного проекта.

Для каждой пары заранее известен правильный ответ.

---

# 47. Edge Cases

Обязательно тестировать:

1. одинаковая квартира с разной ценой;
2. одинаковая квартира с разной площадью из-за округления;
3. разные квартиры одинаковой планировки;
4. один этаж и площадь, но разные номера;
5. одинаковый рендер у нескольких квартир;
6. агент скопировал текст;
7. квартира снята и опубликована заново;
8. застройщик изменил ID;
9. корпус переименован;
10. адрес изменился после ввода дома;
11. вторичка без номера квартиры;
12. один собственник разместил объект на двух площадках;
13. один агент разместил 50 разных квартир;
14. типовая карточка «от 4,5 млн»;
15. пользователь принёс устаревшую ссылку.

# 50. Критерий готовности Deduplication Model

Модель считается готовой, если система умеет корректно обработать:

1. одну квартиру с тремя источниками;
2. две разные квартиры одинаковой планировки;
3. одну квартиру с разными ценами;
4. одну квартиру с разными ипотечными сценариями;
5. вторичку без номера квартиры;
6. дом с несколькими объявлениями;
7. пользовательскую ссылку на уже известный объект;
8. ошибочно объединённый объект и split;
9. пропущенный дубль и ручной merge;
10. неразрешимый случай с manual_review;
11. рекламную типовую планировку;
12. устаревшее повторное объявление;
13. конфликт площади;
14. конфликт адреса;
15. один объект с несколькими продавцами.

# 51. Главный принцип для coding-agent

Нельзя строить дедупликацию как:

```text
похожи → удалить один
```

Правильная модель:

```text
Raw Offer
    ↓
Normalization
    ↓
Candidate Generation
    ↓
Feature Comparison
    ↓
Deduplication Decision
    ↓
Physical Property Cluster
    ↓
несколько Offer сохраняются
```

Главное правило:

> Дедупликация объединяет идентичность объекта, но не уничтожает различия между предложениями.

Именно различия между Offer могут оказаться полезными пользователю:

- другая цена;
- другая акция;
- более свежие данные;
- другой продавец;
- другой способ покупки.

Поэтому конечная цель дедупликации — не «убрать повторы», а построить единую достоверную карточку физического объекта со всеми найденными предложениями и источниками.
