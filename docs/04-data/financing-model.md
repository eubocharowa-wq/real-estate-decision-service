# Financing Model — MVP v1

## 1. Назначение документа

Этот документ описывает единую модель финансирования покупки недвижимости для MVP.

Модель нужна, чтобы сервис мог корректно отвечать на запросы вроде:

- «Найди квартиру до 5 млн по семейной ипотеке».
- «Нужен вариант без первоначального взноса».
- «Есть 2 млн своих, больше 70 тысяч в месяц платить не могу».
- «Что выгоднее: рассрочка от застройщика или ипотека?».
- «Подходит ли именно эта квартира под заявленную программу?».

Главный принцип:

> Финансирование — не характеристика квартиры сама по себе. Это отдельный слой условий сделки, который должен быть связан с конкретным объектом, конкретным предложением, конкретной программой и датой актуальности.

Система не должна считать рекламную фразу «семейная ипотека», «ставка от 3%» или «без первоначального взноса» подтверждённым условием конкретной сделки без проверки применимости.

---

# 2. Основные сущности

Для MVP необходимо разделять минимум пять сущностей:

1. `FinancingProgram` — ипотечная или иная финансовая программа.
2. `FinancingOffer` — конкретное предложение банка / застройщика / партнёра.
3. `Promotion` — акция или специальное условие.
4. `PropertyFinancingEligibility` — применимость программы к конкретному объекту.
5. `UserFinancingProfile` — финансовые условия и ограничения пользователя.

Схема:

```text
UserFinancingProfile
        ↓
FinancingProgram
        ↓
FinancingOffer
        ↓
PropertyFinancingEligibility
        ↓
Property / Offer
```

Дополнительно:

```text
Promotion
   ↘ FinancingOffer
   ↘ Property / Offer
```

---

# 3. Почему нельзя хранить всё внутри карточки квартиры

Неправильная модель:

```yaml
family_mortgage: true
rate: 3.5
initial_payment: 0
```

Она опасна, потому что:

- ставка может относиться только к части срока;
- программа может действовать только для определённых категорий заемщиков;
- первоначальный взнос может зависеть от банка;
- цена объекта может меняться при использовании субсидированной программы;
- акция может распространяться не на все квартиры;
- условия могут закончиться завтра;
- заявленное условие может требовать отдельного одобрения банка.

Правильнее хранить связи и доказательства.

# 5. Версионирование правил

Финансовые программы меняются.

Поэтому нельзя просто хранить:

```yaml
family_mortgage:
  initial_payment: 20
```

Нужно хранить версию правил:

```yaml
rule_version:
  effective_from:
  effective_until:
  collected_at:
  source:
```

Если условия программы изменились, создаётся новая версия, а старая сохраняется для истории.

Главный принцип:

> Финансовое правило всегда должно быть привязано ко времени.

# 6. Eligibility Rules — требования программы

Программа должна содержать структурированные правила применимости.

Группы правил:

### Заёмщик

- возраст;
- семейное положение;
- наличие детей;
- возраст детей;
- гражданство;
- регистрация;
- занятость;
- подтверждение дохода;
- требования к созаемщикам;
- кредитная история;
- другие условия.

### Объект

- тип недвижимости;
- первичный / вторичный рынок;
- застройщик;
- проект;
- стадия строительства;
- готовность;
- регион;
- стоимость;
- юридическая схема сделки.

### Финансы

- минимальный первоначальный взнос;
- максимальная сумма кредита;
- максимальная стоимость объекта;
- ставка;
- срок;
- требования к страховке;
- комиссии;
- дополнительные платежи.

# 7. Нельзя автоматически решать право пользователя на программу

Система может определить:

### `likely_eligible`
Данные пользователя предварительно соответствуют известным правилам.

### `likely_not_eligible`
Есть явное противоречие правилам.

### `needs_confirmation`
Не хватает данных или требуется банковская проверка.

### `unknown`
Правила или данные неполные.

Сервис не должен писать:

> «Вам одобрена семейная ипотека».

Без фактического банковского решения.

Правильная формулировка:

> «По указанным данным программа предварительно может вам подойти. Окончательное решение принимает банк».

Каждое ограничение имеет приоритет:

- `must`

- `neutral`
- `avoid`
- `exclude`

Пример:


# 16. Проверка программы на конкретном объекте

Алгоритм:

1. Есть ли программа вообще?
2. Активна ли она на текущую дату?
3. Подходит ли тип объекта?
4. Подходит ли рынок — новостройка / вторичка / дом?
5. Подходит ли конкретный застройщик / проект?
6. Подходит ли конкретная квартира?
7. Есть ли ограничения по цене?
8. Есть ли ограничения по сумме кредита?
9. Какой минимальный ПВ?
10. Есть ли особые условия банка?
11. Меняется ли цена объекта?
12. Есть ли обязательные услуги?
13. Действует ли акция сегодня?
14. Есть ли подтверждающий источник?
15. Нужна ли дополнительная ручная проверка?

# 17. Проверка семейной ипотеки

Семейная ипотека моделируется как обычный `FinancingProgram` со своей версией правил.

Запрещено хардкодить текущие условия программы напрямую в продуктовую модель.

Почему:

- правила могут меняться;
- лимиты могут меняться;
- допустимые объекты могут меняться;
- банковские предложения отличаются;
- региональные условия могут отличаться.

Правильная архитектура:

```text
Family Mortgage
      ↓
Rule Version
      ↓
Bank Offer
      ↓
Property Eligibility
      ↓
User Eligibility
```

# 19. Акция и ипотечная программа — не одно и то же

Пример:

> «Семейная ипотека без ПВ»

может фактически состоять из:

1. государственной / банковской ипотечной программы;
2. маркетинговой акции застройщика;
3. особого механизма формирования первоначального взноса;
4. увеличенной цены квартиры;
5. ограниченного списка квартир.

Поэтому система должна разложить предложение на составляющие.

# 21. Важные параметры рассрочки

Сервис должен различать:

- равномерные платежи;
- минимальные платежи + крупный финальный платёж;
- рассрочку до сдачи;
- рассрочку с переходом в ипотеку;
- беспроцентную;
- рассрочку с удорожанием;
- рассрочку только на конкретные квартиры.

Нельзя сравнивать рассрочку и ипотеку только по «платежу в месяц».

# 24. Пример: один объект, три сценария

Объект стоит 5 000 000 ₽.

Сценарий A:
- семейная ипотека;
- ПВ 1 000 000;
- платёж X.

Сценарий B:
- акция застройщика;
- ПВ 0;
- цена увеличивается;
- платёж Y.

Сценарий C:
- рассрочка;
- ПВ 500 000;
- крупный платёж через 12 месяцев.

Сервис должен сравнивать именно сценарии, а не только сам объект.

На карточке объекта:

### Финансирование

**Семейная ипотека**
Статус: предварительно подходит / подтверждено / требуется проверка

**Первоначальный взнос**
От ...

**Ежемесячный платёж**
Оценка при указанных условиях

**Акция**
Описание + срок действия

**Важно**
Цена или условия могут отличаться при выборе другой программы.

# 26. Статусы достоверности

Для финансовых данных особенно строго используем:

- `confirmed`
- `claimed`
- `unconfirmed`
- `conflicting`
- `stale`
- `unknown`

### confirmed

Условие подтверждено надёжным актуальным источником и применимо к конкретному объекту.

### claimed

Условие заявлено в рекламе / на сайте.

### unconfirmed

Нет достаточного подтверждения применимости.

### conflicting

Источники противоречат друг другу.

### stale

Срок актуальности истёк либо данные давно не проверялись.

# 30. OpenClaw не должен самостоятельно

- объявлять пользователя подходящим под ипотеку;
- считать рекламную ставку реальной ставкой пользователя;
- считать «без ПВ» подтверждённым без механизма;
- считать программу действующей без проверки даты;
- переносить акцию одного ЖК на другой;
- применять общую акцию к конкретной квартире без подтверждения;
- игнорировать изменение цены при субсидировании;
- придумывать банк;
- вычислять отсутствующие условия из рекламы;
- заменять банковское одобрение своим выводом.

# 31. Логика обработки запроса

Пример:

> «Тула, до 5 млн, семейная ипотека, без первоначального взноса».

Система:

1. Находит объекты до 5 млн.
2. Проверяет наличие связи с семейной ипотекой.
3. Проверяет актуальную версию программы.
4. Проверяет применимость к конкретному объекту.
5. Проверяет предложения банков / застройщика.
6. Ищет варианты нулевого ПВ.
7. Проверяет механизм нулевого ПВ.
8. Проверяет, меняется ли цена.
9. Рассчитывает сценарий.
10. Маркирует достоверность.
11. Отбирает подтверждённые и вероятные варианты.
12. Не смешивает их в один статус.

---

# 32. Результаты поиска по уровню уверенности

Рекомендуемые группы:

## Подтверждённо подходит

Ключевые обязательные финансовые условия подтверждены.

## Предварительно подходит

По доступным данным условия совпадают, но нужна дополнительная проверка.

## Возможно подходит

Есть рекламное или неполное подтверждение.

## Не подходит

Есть явное несоответствие обязательному условию.

## Недостаточно данных

Нельзя сделать вывод.

---

# 33. Если точных вариантов нет

Пример:

> Нет подтверждённых объектов до 5 млн с семейной ипотекой и ПВ 0.

Система не должна подменять результат.

Она показывает:

**Точных подтверждённых совпадений нет.**

И возможные сценарии:

- ПВ до 300 тыс. → N вариантов;
- бюджет до 5,3 млн → N вариантов;
- семейная ипотека, но ПВ требует уточнения → N потенциальных вариантов.

Пользователь сам решает, ослаблять ли условие.

---

# 34. Сравнение ипотека vs рассрочка

Сравнение должно учитывать:

- деньги на входе;
- ежемесячную нагрузку;
- крупные будущие платежи;
- полную стоимость;
- срок;
- риск изменения условий;
- необходимость последующего кредита;
- срок въезда;
- удорожание объекта.

Нельзя выводить:

> «Рассрочка выгоднее»

только потому, что первый ежемесячный платёж ниже.

# 40. Безопасность и точность

Финансовый слой должен работать консервативно.

Если программа не подтверждена:

> «Требует проверки».

Если ставка рекламная:

> «Ставка от …, точные условия зависят от программы».

Если пользователь предварительно соответствует:

> «Может подойти».

Если данных недостаточно:

> «Недостаточно данных для вывода».

Нельзя создавать ложное ощущение банковского одобрения или гарантированной сделки.

---

# 41. Критерий готовности модели

`financing-model.md` считается готовым для MVP, если модель позволяет корректно представить:

1. стандартную ипотеку;
2. семейную ипотеку;
3. акционную ставку;
4. рекламную ставку «от»;
5. реальный первоначальный взнос;
6. заявленный ПВ 0;
7. ПВ 0 с удорожанием;
8. рассрочку;
9. рассрочку с финальным крупным платежом;
10. один объект с несколькими схемами покупки;
11. программу, которая действует не на все квартиры;
12. противоречащие источники;
13. просроченную акцию;
14. ситуацию, где пользователю программа только предварительно подходит;
15. ситуацию, где точных финансовых совпадений нет.

# 42. Главный принцип для coding-agent

Финансовая модель должна отвечать не на вопрос:

> «У этой квартиры есть семейная ипотека?»

а на вопрос:

> «Можно ли конкретному пользователю купить конкретный объект по конкретной программе на конкретных условиях и насколько эти условия подтверждены сейчас?»

Правильная последовательность:

> программа → актуальная версия правил → предложение банка / застройщика → применимость к объекту → применимость к пользователю → расчёт сценария → проверка источников → статус достоверности → объяснение.

Никакая рекламная надпись не должна автоматически становиться фактом.
