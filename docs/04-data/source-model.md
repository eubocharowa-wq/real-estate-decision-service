# Source Model — MVP v1

## 1. Назначение документа

Этот документ описывает, как сервис хранит происхождение данных о недвижимости, финансовых программах, акциях, инфраструктуре и других фактах.

Source Model нужен для того, чтобы пользователь видел не только результат, но и понимал:

- откуда взялась информация;
- когда она была получена;
- насколько она свежая;
- является ли она подтверждённым фактом, заявлением продавца или неподтверждённой информацией;
- есть ли расхождения между источниками;
- какой источник считать приоритетным;
- что нужно перепроверить.

Главный принцип:

> В системе не должно существовать важных фактов без происхождения, если происхождение можно установить.

Источник — это не просто URL карточки объекта. Источник должен быть связан с конкретными данными и конкретной датой их получения.

---

# 2. Зачем Source Model критичен для продукта

УТП сервиса строится не только на подборе, но и на объяснимости.

Пользователь должен иметь возможность увидеть:

> Цена 4 890 000 ₽  
> Источник: сайт застройщика  
> Проверено: сегодня

или:

> Без первоначального взноса  
> Статус: заявлено застройщиком  
> Применимость к этой квартире пока не подтверждена

или:

> Площадь: 42,1 м²  
> На сайте застройщика: 42,1 м²  
> На площадке: 41,8 м²  
> Есть расхождение — требуется уточнение

Source Model делает это технически возможным.

---

# 3. Основные сущности

Для MVP вводим:

1. `Source` — сам источник.
2. `SourceSnapshot` — состояние страницы / ответа источника в конкретный момент.
3. `FieldEvidence` — доказательство конкретного значения поля.
4. `SourceConflict` — конфликт данных между источниками.
5. `CollectionRun` — конкретный запуск OpenClaw / коннектора / ручного сбора.
6. `SourcePolicy` — правила работы с конкретным источником.

Схема:

```text
Source
  ↓
CollectionRun
  ↓
SourceSnapshot
  ↓
FieldEvidence
  ↓
Normalized Entity
```

При расхождении:

```text
FieldEvidence A
        ↘
      SourceConflict
        ↗
FieldEvidence B
```

# 6. Source Priority — приоритет источника

Приоритет не означает, что источник всегда прав.

Он используется как один из факторов разрешения конфликтов.

Пример базовой иерархии для конкретного типа данных:

## Цена конкретной квартиры в новостройке

1. актуальная карточка конкретной квартиры на сайте застройщика;
2. официальный фид застройщика;
3. официальный сайт проекта;
4. партнёрская площадка;
5. классифайд;
6. агентский сайт;
7. пользовательская ссылка без подтверждения.

## Правила государственной программы

1. официальный государственный источник;
2. официальный банк;
3. официальный застройщик;
4. партнёр;
5. рекламная площадка.

Но эта иерархия должна быть настраиваемой по типу поля.

# 7. Trust Level — уровень доверия

`trust_level` не является абсолютной оценкой качества источника.

Значения:

- `authoritative`
- `primary`
- `secondary`
- `user_provided`
- `unknown`

### authoritative

Официальный нормативный / государственный источник для соответствующего типа данных.

### primary

Первоисточник конкретного коммерческого факта.

Например, застройщик для цены своей квартиры.

### secondary

Площадка, агентство, агрегатор.

### user_provided

Источник, принесённый пользователем.

### unknown

Нельзя определить уровень.

# 9. SourcePolicy — правила работы с источником

Для каждого подключённого источника необходимо иметь конфигурацию.

Поля:

- `source_id`
- `allowed_collection_methods`
- `preferred_method`
- `update_frequency`
- `fields_expected`
- `fields_not_trusted_without_confirmation`
- `rate_limit_notes`
- `authentication_notes`
- `manual_review_required`
- `parser_version`

Пример:

```yaml
source_id: developer_example
preferred_method: http_fetch

  - http_fetch
  - browser_agent
update_frequency: "every_6_hours"

  - listing_price
  - area
  - floor
  - availability
fields_not_trusted_without_confirmation:
  - zero_initial_payment
  - advertised_monthly_payment
```

# 12. FieldEvidence — доказательство конкретного поля

Это одна из центральных сущностей проекта.

Пример:

```yaml
field_evidence:
  entity_type: property_offer
  entity_id: offer_145
  field: listing_price
  value: 4890000
  source_id: developer_example
  snapshot_id: snapshot_123
  collected_at: 2026-08-12T18:40:00+03:00
  verification_status: confirmed
```

Для финансовой акции:

```yaml
field: zero_initial_payment
value: true
verification_status: claimed
```

То есть одно и то же поле может иметь несколько Evidence из разных источников.

# 13. Verification Status

Единый набор статусов:

- `confirmed`
- `claimed`
- `unconfirmed`
- `conflicting`
- `stale`
- `unknown`

Эти статусы должны одинаково использоваться в:

- property-model;
- financing-model;
- source-model;
- пользовательском интерфейсе.

---

# 14. Как назначается статус confirmed

`confirmed` нельзя назначать просто потому, что информация найдена на сайте.

Для MVP поле может быть `confirmed`, если:

1. найден конкретный факт;
2. источник релевантен этому типу данных;
3. факт относится именно к конкретному объекту / программе;
4. данные достаточно свежие;
5. отсутствует неразрешённый конфликт с более сильным источником.

Пример:

Цена конкретной квартиры на её карточке у застройщика сегодня  
→ может быть `confirmed`.

Рекламный баннер «квартиры от 4,5 млн»  
→ не может подтверждать цену конкретной квартиры.

---

# 15. Claimed

`claimed` используется, когда источник сам заявляет условие, но система не может подтвердить его применимость или объективность.

Примеры:

- «без первоначального взноса»;
- «10 минут до центра»;
- «лучший район»;
- «высокая инвестиционная привлекательность»;
- «ставка от 2,9%».

Пользователю:

> Заявлено источником. Требуется уточнение условий.

---

# 16. Stale — устаревшие данные

Для каждого типа поля должен существовать допустимый возраст данных.

Примерная логика MVP:

### Очень быстро меняются

- цена;
- наличие;
- бронь;
- акция;
- ставка;
- первоначальный взнос.

### Средняя изменчивость

- сроки передачи ключей;
- состояние строительства;
- инфраструктурные объекты;
- условия рассрочки.

### Почти статичные

- площадь конкретной квартиры;
- этаж;
- адрес;
- год постройки готового дома.

Конкретные TTL задаются позже в конфигурации.

# 18. Пример конфликта цены

Источник A:

```text
4 890 000 ₽
сайт застройщика
проверено сегодня
```

Источник B:

```text
4 990 000 ₽
классифайд
проверено сегодня
```

Сервис не должен просто выбрать минимальную цену.

Он должен проверить:

- это точно одна квартира?
- одинаковы ли условия покупки?
- одна ли отделка?
- не включена ли скидка?
- не действует ли цена только при определённой ипотеке?

Пока конфликт не разрешён:

> Цена в источниках различается: 4,89–4,99 млн ₽. Требует уточнения.

---

# 19. Разрешение конфликтов

Автоматическое разрешение допустимо только при понятном правиле.

Например:

- один источник свежее;
- один источник относится к конкретной квартире, другой — к типовой планировке;
- один источник первичный, другой вторичный;
- один источник явно содержит старую цену.

Если причина не очевидна:

`manual_required`

или:

`conflicting`

---

# 20. Provenance Chain — цепочка происхождения

Для важных данных должна быть восстанавливаемая цепочка:

```text
Пользователь видит:
Цена = 4 890 000 ₽
        ↓
Normalized field
        ↓
FieldEvidence
        ↓
SourceSnapshot
        ↓
URL
        ↓
CollectionRun
```

Это позволит в будущем:

- объяснять результат;
- проводить аудит;
- исправлять ошибки парсеров;
- проверять работу OpenClaw;
- анализировать качество источников.

---

# 21. Источники, принесённые пользователем

Когда пользователь вставляет ссылку:

- создаётся `Source` типа `user_link`, если источник ещё не зарегистрирован;
- создаётся snapshot;
- агент пытается извлечь данные;
- пользователю показываются распознанные поля;
- пользователь может исправить их.

Исправление пользователя:

- не удаляет автоматически исходные данные;
- создаёт отдельное evidence типа `user_confirmed`.

---

# 22. Ручная экспертная проверка

Если эксперт подтверждает условие вручную:

```yaml
source_type: manual_expert
verification_status: confirmed
```

Нужно хранить:

- кто проверил;
- когда;
- что именно проверено;
- на основании чего;
- комментарий;
- при необходимости приложенный документ / ссылка.

---

# 24. OpenClaw — роль в Source Model

OpenClaw — исполнитель сбора.

Он должен:

1. получить список источников и задач;
2. открыть нужный источник;
3. извлечь только поля, определённые схемой;
4. сохранить URL;
5. сохранить время сбора;
6. вернуть evidence для каждого извлечённого факта;
7. сообщить, если значение не найдено;
8. сообщить о блокировке / CAPTCHA / ошибке;
9. не придумывать отсутствующие данные;
10. не разрешать сложные конфликты самостоятельно.

---

# 25. Что OpenClaw должен возвращать

Пример:

```json
{
  "source_id": "developer_example",
  "url": "https://example.ru/flats/145",
  "collected_at": "2026-08-12T18:40:00+03:00",

  "fields": {
    "listing_price": {
      "value": 4890000,
      "evidence_text": "Стоимость квартиры 4 890 000 ₽",
      "confidence": "high"
    },

    "total_area_m2": {
      "value": 41.8,
      "evidence_text": "Площадь 41,8 м²",
      "confidence": "high"
    },

    "zero_initial_payment": {
      "value": true,
      "evidence_text": "Ипотека без первоначального взноса",
      "confidence": "medium"
    }
  },

  "warnings": [
    "Не удалось подтвердить, что акция применяется именно к квартире №145"
  ]
}
```

---

# 26. Что OpenClaw не должен делать

Запрещено:

- подменять отсутствующие значения логическими догадками;
- выдавать рекламное утверждение за подтверждённый факт;
- считать совпадающие названия доказательством дубля;
- автоматически менять значение в базе без сохранения evidence;
- удалять старое значение без истории;
- скрывать конфликт;
- считать данные актуальными только потому, что страница открылась;
- использовать один источник как доказательство информации другого типа без оснований.

---

# 27. История изменений

Для важных динамических полей необходимо хранить историю.

Минимально:

- цена;
- наличие;
- акции;
- условия финансирования.

Пример:

```text
10.08 — 5 050 000
11.08 — 4 990 000
12.08 — 4 890 000
```

История нужна не только пользователю, но и для обнаружения ошибок.

---

# 28. Source Quality Metrics

В будущем для каждого источника можно считать:

- процент успешных обновлений;
- частоту ошибок;
- средний возраст данных;
- долю конфликтующих полей;
- долю неполных карточек;
- стабильность структуры;
- точность после ручной проверки.

В MVP достаточно заложить архитектуру.

---

# 29. Источник и юридическая допустимость

Техническая возможность прочитать страницу не означает автоматически право систематически использовать данные.

Для каждого внешнего источника в будущем должен существовать `SourcePolicy` с юридическими и техническими заметками.

До подключения источника в массовый автоматизированный сбор необходимо отдельно определить допустимый способ получения и использования данных.

---

# 30. Данные нельзя терять при нормализации

Пример:

Источник пишет:

> «Ипотека 0,1% на первый год»

Нормализатор не должен записать просто:

```yaml
interest_rate: 0.1
```

Нужно сохранить исходную семантику:

```yaml
rate:
  initial_period_rate: 0.1
  initial_period: 12_months
  later_rate: unknown
```

и сохранить evidence оригинального утверждения.

# 33. Data Confidence vs Source Trust

Это разные вещи.

Источник может быть сильным, но конкретный факт — слабым.

Пример:

Официальный сайт застройщика — `primary`.

Но баннер:

> «Ставка от 0,1%»

не подтверждает конкретную ставку пользователя.

Поэтому:

```text
source trust = primary
field verification = claimed
```

# 36. Приоритет реализации MVP

На первой версии обязательно:

1. реестр источников;
2. URL происхождения;
3. время последней проверки;
4. evidence для цены;
5. evidence для наличия;
6. evidence для финансовых условий;
7. статусы confirmed / claimed / unconfirmed / conflicting / stale / unknown;
8. конфликты;
9. лог OpenClaw / коннекторов;
10. источник для пользовательской ссылки.

Можно позже:

- сложную статистику качества источников;
- полноценное хранение всех snapshots;
- визуальную историю каждого поля;
- автоматические юридические политики;
- сложный аудит изменений parser versions.

# 37. Критерий готовности Source Model

Модель считается готовой для MVP, если система может корректно представить:

1. объект с одним источником;
2. объект с тремя источниками;
3. одинаковую цену из двух источников;
4. конфликтующие цены;
5. устаревшую цену;
6. рекламную акцию;
7. подтверждённую цену конкретной квартиры;
8. пользовательскую ссылку;
9. ручное экспертное подтверждение;
10. недоступный источник;
11. ошибку OpenClaw;
12. поле, для которого нет доказательства;
13. изменение цены во времени;
14. финансовое условие с отдельным источником;
15. объект, где разные поля получены из разных источников.

# 38. Главный принцип для coding-agent

Не строить модель в формате:

```text
объект → один URL → набор значений
```

Правильная модель:

```text
объект / предложение
        ↓
нормализованные поля
        ↓
FieldEvidence
        ↓
SourceSnapshot
        ↓
Source
```

Одно поле может иметь несколько источников.

Одно объявление может содержать данные о нескольких сущностях.

Один физический объект может присутствовать в нескольких объявлениях.

Система должна сохранять происхождение данных, а не только их последнее значение.

Главное правило:

> Нет источника — нет уверенного факта. Есть реклама — это ещё не подтверждение. Есть конфликт — пользователь должен знать, что данные расходятся.
