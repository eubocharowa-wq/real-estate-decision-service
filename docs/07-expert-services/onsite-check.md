# Onsite Check — MVP v1

## 1. Назначение документа

Этот документ описывает услугу выездной проверки объекта.

Выезд используется тогда, когда важную для пользователя информацию невозможно надёжно получить дистанционно.

Главный принцип:

> Выезд — не стандартный шаг после подбора. Он нужен только тогда, когда физическая проверка действительно может изменить решение пользователя.

---

# 2. Для каких объектов

- вторичная квартира;
- готовая новостройка;
- дом;
- townhouse;
- участок;
- объект после ремонта;
- объект перед покупкой / приёмкой.

---

# 3. Типы выездной проверки

Для MVP:

- `visual_property_check`
- `neighborhood_check`
- `condition_check`
- `house_and_land_check`
- `pre_purchase_visit`

Не называть техническим обследованием то, что является обычным визуальным осмотром.

---

# 4. Когда нужен профильный специалист

Если пользователь просит:

- проверить конструктив;
- инженерные системы;
- фундамент;
- скрытые дефекты;
- строительные нормы;

нужен `technical_specialist / property_inspector`.

Обычный эксперт по недвижимости не должен выдавать техническое заключение.

---

---

# 6. Scope

Выезд всегда должен иметь checklist.

Пример квартиры:

- подъезд;
- лифт;
- двор;
- парковка;
- шум;
- состояние ремонта;
- окна;
- запахи;
- визуальные дефекты;
- соответствие фотографиям.

---

# 7. Дом

Checklist:

- внешний вид;
- кровля визуально;
- стены;
- участок;
- подъездная дорога;
- вода;
- электричество;
- газ;
- канализация;
- отопление;
- соседство;
- фактическое состояние.

---

# 8. Neighborhood Check

Если пользователь живёт в другом городе:

можно проверить:

- дорогу;
- двор;
- окружение;
- реальную удалённость объектов;
- шум;
- состояние территории;
- ближайшую инфраструктуру.

---

# 9. Что не проверяется визуально

Нельзя подтверждать без оснований:

- юридическую чистоту;
- скрытые дефекты;
- качество фундамента;
- исправность скрытой проводки;
- качество воды;
- границы участка;
- наличие зарегистрированных прав.

---

# 10. Pre-visit Context

Эксперт получает:

- Property;
- UserRequest;
- MatchResult;
- critical unknowns;
- фотографии;
- sources;
- конкретные вопросы пользователя.

---

# 11. User-specific Scope

Checklist должен учитывать запрос.

Пример:

Пользователь:

> «Я работаю из дома, очень важна тишина».

Выезд должен отдельно проверить шум.

---

# 12. Другой пример

> «Две машины».

Проверить реальную парковочную ситуацию.

---

# 13. Onsite Checklist Item

```yaml
check_item:
  criterion:
  status:
  observation:
  evidence:
  confidence:
  requires_specialist:
```

---

# 14. Status

- `confirmed`
- `not_confirmed`
- `observed_issue`
- `unable_to_check`
- `requires_specialist`

---

# 15. Evidence

Для выезда:

- фото;
- видео;
- заметка;
- измерение;
- timestamp.

---

# 16. Не использовать фото без контекста

Фото должно быть связано с check item.

---

# 17. Measurements

Если делается измерение:

- тип;
- устройство;
- точность;
- значение.

Не выдавать бытовое измерение за профессиональную экспертизу.

---

# 18. Noise

Можно фиксировать:

- субъективное наблюдение;
- время;
- источник шума.

Если используется измеритель:

отдельно указать метод.

---

# 19. Utilities

Дом:

```text
газ
```

нельзя считать confirmed только потому, что видна труба.

Нужно различать:

- visually observed;
- seller claim;
- document confirmed.

---

---

# 21. Result Example

```text
Подтверждено:
✓ подъезд в хорошем состоянии
✓ окна во двор
✓ парковка вечером заполнена примерно на 90%

Обнаружено:
! слышен постоянный шум с дороги

Не проверено:
— документы
— скрытая электропроводка
```

---

# 22. Observed Fact vs Expert Opinion

Структурно разделять:

### Observation

> На стене видна трещина.

### Interpretation

> Требуется технический специалист для оценки причины.

Не писать:

> Дом аварийный.

без компетентного заключения.

---

# 23. Canonical Update

Выезд может обновить:

- condition;
- parking observation;
- noise observation;
- finishing;
- physical availability;
- utilities status evidence.

---

# 24. Data Confidence Update

Выезд повышает confidence только по проверенным полям.

---

# 25. Matching Update

Пример:

До:

```text
quiet_area = unknown
```

После:

```text
road_noise = observed_issue
```

Если тишина была high preferred:

MatchScore может снизиться.

---

# 26. Другой пример

До:

```text
parking = claimed
```

После:

```text
parking_capacity = poor_observed
```

Результат пересчитывается.

---

# 27. Onsite May Exclude Property

Если обнаружено нарушение must:

объект может перейти в hard_fail.

Это нормальная функция проверки.

---

# 28. Inspection vs Viewing

Выезд эксперта должен отличаться от обычного просмотра.

У него есть:

- scope;
- checklist;
- evidence;
- structured report;
- связь с UserRequest.

---

# 29. Remote Buyer Scenario

Особенно полезно для:

- переезда;
- покупки в другом городе;
- пользователя, который не может приехать.

---

# 30. Seller Coordination

Операционная часть:

- доступ к объекту;
- согласование времени;
- разрешение на фото;
- контакт продавца/застройщика.

В MVP может выполняться вручную.

---

# 31. Privacy

Не публиковать:

- лица;
- личные вещи;
- документы собственника;

без необходимости.

---

# 32. Safety

Эксперт не должен выполнять опасные действия:

- вскрывать электрощит;
- лезть на кровлю;
- разбирать конструкции;
- заходить в опасные помещения;

если это не входит в профессиональную техническую услугу.

---

# 33. Specialist Escalation

Если обнаружено:

- трещина;
- следы протечек;
- проблемы инженерии;
- фундамент;

результат:

```text
requires_technical_specialist
```

---

# 34. Onsite User Result

Рекомендуемые блоки:

### Что проверили

### Что подтвердилось

### Что не совпало с объявлением

### Что насторожило

### Что невозможно проверить визуально

### Что делать дальше

---

# 35. Before / After Comparison

Можно показывать:

```text
До выезда:
Match 89%
Confidence 61%

После:
Match 81%
Confidence 88%
```

с объяснением причин.

---

# 36. MVP Acceptance Criteria

Сценарий готов, если:

1. создаётся OnsiteRequest;
2. есть scope;
3. scope связан с UserRequest;
4. эксперт получает Property context;
5. работает checklist;
6. можно прикрепить фото;
7. observation отделён от interpretation;
8. есть unable_to_check;
9. можно эскалировать technical specialist;
10. результат обновляет evidence;
11. confidence пересчитывается;
12. Matching пересчитывается;
13. checked/not checked видны пользователю;
14. визуальный осмотр не выдаётся за техническое заключение.

---

# 37. Главный принцип для coding-agent

Нельзя строить выезд как:

```text
заявка → свободный комментарий эксперта
```

Правильно:

```text
UserRequest
+
Property
+
Critical Unknowns
↓
Onsite Scope
↓
Checklist
↓
Observations + Evidence
↓
Structured OnsiteResult
↓
Canonical Data / Confidence
↓
Matching Recalculation
```

Ценность выезда — не сам факт посещения объекта, а устранение конкретной неопределённости перед решением.
