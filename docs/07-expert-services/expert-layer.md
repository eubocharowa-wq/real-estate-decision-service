# Expert Layer — MVP v1

## 1. Назначение документа

Этот документ описывает экспертный слой сервиса — момент, когда автоматического подбора, сравнения и объяснения недостаточно и пользователю требуется участие человека.

Экспертный слой не должен превращать продукт в обычное агентство недвижимости.

Его задача:

> подключить человека только там, где автоматический сервис уже сузил задачу и ясно понимает, что именно нужно проверить, объяснить или сравнить.

Базовый пользовательский путь:

```text
Описать задачу
      ↓
Подобрать
      ↓
Сравнить
      ↓
Разобраться / проверить при необходимости
      ↓
Принять решение
```

Эксперт появляется **после цифрового слоя**, а не вместо него.

---

# 2. Зачем продукту экспертный слой

Недвижимость содержит задачи, которые плохо решаются только алгоритмом:

- противоречивые данные;
- сложные условия сделки;
- документы;
- юридические нюансы;
- индивидуальные вопросы пользователя;
- непонятные ипотечные акции;
- необходимость выбрать из 2–5 почти равных вариантов;
- проверка реального состояния объекта;
- ситуация, где данные отсутствуют в публичных источниках.

Экспертный слой закрывает этот разрыв.

---

# 3. Что экспертный слой НЕ должен делать

Экспертный слой не должен:

- быть обязательным для каждого пользователя;
- скрывать результаты автоматического подбора;
- искусственно создавать необходимость консультации;
- навязывать объект из-за комиссии;
- заменять Matching Engine субъективным «мне кажется»;
- выдавать юридическое заключение без соответствующей квалификации;
- подтверждать ипотеку вместо банка;
- подменять техническое обследование, если требуется профильный специалист;
- создавать впечатление, что эксперт «проверил всё», если проверена только часть вопросов.

---

# 4. Основной принцип

Экспертная услуга всегда должна начинаться с конкретной задачи.

Плохо:

> «Нужна консультация риелтора?»

Правильно:

> «В двух источниках различается цена этой квартиры. Проверить актуальную стоимость и условия акции?»

или:

> «У вас осталось три варианта. Разобрать их вместе и определить, какой лучше решает вашу задачу?»

Базовая сущность:

`ExpertRequest`

```yaml

  request_id:
  user_id:
  request_type:
  source_context:
  property_ids:
  comparison_id:
  user_request_id:
  questions:
  priority:
  status:
  required_specialist:
  created_at:
```

---

# 6. Типы Expert Request

Для MVP:

- `information_verification`
- `document_review`
- `choice_assistance`
- `property_analysis`
- `consultation`
- `onsite_check`
- `transaction_question`

---

# 7. Information Verification

Услуга:

> проверить конкретную информацию об объекте или условиях покупки.

Примеры:

- актуальная цена;
- действует ли акция;
- доступна ли квартира;
- подходит ли объект под конкретную ипотечную программу;
- какой реальный первоначальный взнос;
- изменяется ли цена при субсидированной ипотеке;
- срок сдачи / передачи ключей;
- что входит в отделку.

---

# 8. Document Review

Услуга:

> разобрать документ и объяснить пользователю его содержание и потенциально значимые условия.

Примеры:

- договор бронирования;
- ДДУ;
- договор купли-продажи;
- условия акции;
- ипотечные условия;
- проектная документация;
- документы продавца;
- документы объекта.

Важно:

> формальная юридическая экспертиза должна выполняться квалифицированным юристом, если вопрос требует юридического заключения.

Сервис не должен обозначать обычный AI-анализ или комментарий риелтора как юридическое заключение.

---

# 9. Choice Assistance

Услуга:

> помочь выбрать из нескольких финальных вариантов.

Это один из наиболее сильных экспертных сценариев продукта.

Вход:

```text
2–5 объектов
+ исходный UserRequest
+ MatchResult
+ критичные unknowns
+ финансовые сценарии
```

Эксперт не начинает анализ «с нуля».

Он получает уже подготовленную сравнительную структуру.

---

# 10. Property Analysis

Услуга:

> подробно разобрать один выбранный объект.

Возможные блоки:

- соответствует ли исходной задаче;
- сильные стороны;
- компромиссы;
- стоимость покупки;
- финансовые условия;
- район;
- сроки;
- риски;
- неизвестные данные;
- альтернативы на рынке.

---

# 11. Consultation

Общий экспертный разговор нужен, если задача не укладывается в конкретную проверку.

Например:

> «Я переезжаю из другого региона и вообще не понимаю, какую стратегию покупки выбрать».

Но даже консультация должна получать существующий `UserRequest`, если он уже сформирован.

---

# 12. Onsite Check

Выездная проверка — не основной entry point продукта.

Она предлагается, когда:

- объект уже выбран или вошёл в финальный shortlist;
- дистанционно нельзя проверить важные характеристики;
- осмотр действительно может изменить решение.

Примеры:

- состояние вторичной квартиры;
- качество ремонта;
- шум;
- окружение;
- подъезд;
- дом;
- участок;
- фактические коммуникации;
- подъездная дорога.

---

# 13. Не делать выезд обязательной ступенью

Правильная логика:

```text
цифровая проверка
↓
если достаточно данных → решение
↓
если остаётся физический unknown → onsite
```

---

# 14. Expert Trigger

Система может определить, когда экспертная помощь полезна.

Но это только рекомендация.

`expert_trigger`:

- critical unknown;
- unresolved conflict;
- low confidence;
- finalist comparison;
- document uploaded;
- user explicitly asks;
- onsite-only criterion;
- complex transaction condition.

---

# 15. Trigger Example

```yaml
expert_trigger:
  type: information_verification
  reason: "zero_initial_payment_unconfirmed"
  property_id: prop_145
  priority: high
```

UI:

> Условие «без первоначального взноса» пока подтверждено только рекламной страницей. Можно запросить экспертную проверку конкретно по этой квартире.

---

# 16. Не продавать услугу через искусственную неопределённость

Запрещено:

- намеренно не обновлять данные;
- скрывать источник;
- показывать false uncertainty;
- понижать confidence ради продажи экспертной услуги.

Expert Trigger должен возникать из реального состояния данных.

---

# 17. Expert Context Package

Эксперт должен получать не просто сообщение пользователя.

Формируется:

`ExpertContextPackage`

```yaml
expert_context:
  user_request:
  properties:
  match_results:
  comparison:
  financing_scenarios:
  critical_unknowns:
  conflicts:
  evidence:
  source_links:
  user_questions:
```

---

# 18. Зачем Context Package

Эксперт не должен повторно задавать пользователю:

- какой бюджет;
- какой район;
- сколько детей;
- что обязательно;
- какой ПВ;
- что уже нашли.

Если это уже есть в `UserRequest`, оно передаётся автоматически.

---

# 19. Expert Output

Эксперт возвращает структурированный результат.

`ExpertResult`:

```yaml
expert_result:
  request_id:
  status:
  checked_items:
  findings:
  confirmed:
  unconfirmed:
  conflicts:
  risks:
  recommendations:
  next_actions:
  evidence:
  specialist:
  completed_at:
```

---

# 20. Checked Items

Очень важно показать область проверки.

Пример:

```text
Проверено:
✓ цена
✓ наличие
✓ условия акции

Не проверялось:
— юридическая чистота
— техническое состояние квартиры
```

Это защищает пользователя от ложного ощущения полной проверки объекта.

# 23. Unable to Verify

Эксперт имеет право вернуть:

> Не удалось подтвердить.

Это корректный результат.

Он лучше выдуманного заключения.

---

# 24. Expert Evidence

Экспертное подтверждение должно иметь evidence.

Например:

- email;
- официальный документ;
- ответ застройщика;
- банковский документ;
- ссылка;
- фото;
- комментарий после звонка;
- акт осмотра.

---

# 25. Manual Evidence в общей data architecture

Результат экспертной проверки становится частью Source Model.

```text
ExpertResult
↓
Manual Evidence
↓
FieldEvidence
↓
Canonical Update
↓
Confidence Recalculation
↓
Match Recalculation
```

---

# 26. Эксперт не создаёт параллельную базу

Все подтверждённые экспертные данные должны попадать в общую модель provenance.

Не нужно отдельной «таблицы заметок риелтора», которая не связана с canonical data.

# 27. Expert Roles

Система должна различать тип специалистов.

Для MVP:

- `real_estate_expert`
- `lawyer`
- `mortgage_specialist`
- `property_inspector`
- `technical_specialist`

---

# 28. Real Estate Expert

Может:

- помочь сравнить;
- проверить коммерческую информацию;
- разобрать рыночный контекст;
- проверить застройщика / проект по доступным данным;
- помочь сформировать стратегию выбора.

---

# 29. Lawyer

Подключается для:

- юридического заключения;
- договора;
- прав собственности;
- обременений;
- сложной схемы сделки;
- рисков документов.

Не заменять его AI-анализом.

---

# 30. Mortgage Specialist

Может:

- проверить банковскую программу;
- разобрать условия;
- сравнить ипотечные сценарии;
- объяснить структуру ПВ;
- проверить реальность рекламного предложения.

Но банковское одобрение принимает банк.

---

# 31. Property Inspector

Для физического осмотра:

- дефекты;
- ремонт;
- инженерные системы;
- качество строительства;
- состояние объекта.

---

# 32. Expert Routing

`required_specialist` определяется типом задачи.

Пример:

```text
разница в цене
→ real_estate_expert

условия семейной ипотеки
→ mortgage_specialist

ДКП
→ lawyer

трещины в доме
→ property_inspector
```

---

# 33. Multi-specialist Request

Одна задача может требовать нескольких специалистов.

Например:

> вторичная квартира + документы + техническое состояние.

Тогда создаются связанные expert requests.

# 34. User-facing Expert Menu

Вместо абстрактного:

> Услуги

лучше:

### Проверить информацию

### Проверить объект на месте
Если дистанционной проверки недостаточно.

# 39. Priorities

- `urgent`

# 44. Expert Quality

В будущем можно отслеживать:

- response time;
- verification success;
- corrections;
- user satisfaction;
- disagreement rate;
- result completeness.

---

# 45. Commercial Neutrality

Эксперт не должен получать ranking на основе:

- комиссии;
- партнёрства;
- рекламного бюджета.

Если существует коммерческая связь с объектом, она должна быть раскрыта отдельно.

---

# 46. Expert Recommendation Structure

Экспертная рекомендация должна разделять:

### Факты

> Цена подтверждена на такую-то дату.

### Вывод

> При вашем бюджете объект укладывается.

### Компромисс

> Но ремонт увеличит входной бюджет.

### Неизвестное

> Не подтверждён срок освобождения квартиры.

---

# 47. Не использовать «лучший объект» без контекста

Правильнее:

> Из трёх вариантов этот лучше соответствует вашим обязательным условиям.

а не:

> Это лучший ЖК.

# 54. Expert Layer и Data Confidence

Expert Layer должен повышать confidence только по реально проверенным полям.

Пример:

До:

```text
ПВ 0
verification = claimed
```

После звонка и письменного подтверждения:

```text
verification = confirmed/manual
```

---

# 55. Expert Layer и Matching

После изменения canonical data:

```text
Expert Result
↓
Field Evidence
↓
Canonical Update
↓
Confidence Update
↓
MatchResult Recalculation
```

---

# 56. Пример

До проверки:

```text
Match: 91%
Confidence: 62%
ПВ 0 — claimed
```

После проверки:

```text
ПВ 0 подтверждено для квартиры
```

Новый результат:

```text
Match: 91%
Confidence: 88%
```

Match не обязан меняться, потому что соответствие уже было высоким.

Меняется надёжность.

---

# 57. Другой пример

До проверки:

```text
ПВ 0 — claimed
```

После:

```text
ПВ минимум 20%
```

Если ПВ 0 был must:

```text
eligible_with_unknowns
→ hard_fail
```

Экспертная проверка может ухудшить результат — это нормально.

---

# 58. Не скрывать отрицательный результат

Если проверка показала, что объект не подходит:

это ценная услуга.

Не нужно пытаться «спасти сделку».

---

# 59. Expert Layer в MVP

На первой версии достаточно:

1. создать expert request;
2. прикрепить property / comparison context;
3. выбрать тип запроса;
4. передать его специалисту;
5. изменить status;
6. сохранить structured result;
7. добавить manual evidence;
8. обновить confidence / matching;
9. показать результат пользователю.

---

# 60. Что не обязательно в MVP

Можно отложить:

- marketplace специалистов;
- автоматическое распределение по рейтингу;
- встроенную телефонию;
- оплату внутри сервиса;
- календарь выездов;
- сложный CRM;
- чат в реальном времени;
- мобильное приложение эксперта;
- contractor network;
- SLA optimization.

---

# 61. Internal Admin

- пользовательская задача;

# 64. Expert Trigger Rules для MVP

Триггер может быть рекомендован, если:

```text
critical_unknown_count > 0
```

или:

```text
critical_conflict_count > 0
```

или:

```text
finalist_count <= 5
```

и пользователь хочет помощь.

Но request создаётся только после действия пользователя, кроме внутренних manual review задач data layer.

---

# 65. Data Review vs User Expert Service

Это разные сущности.

## Internal Data Review

Нужно системе:

> определить, являются ли две записи дублем.

Пользователь не заказывает это.

## User Expert Service

Пользователь просит:

> проверить условия конкретной квартиры.

Их нельзя смешивать в одной очереди без типа задачи.

---

# 66. Privacy

Эксперту передаются только данные, необходимые для задачи.

Не нужно показывать весь пользовательский профиль, если запрос:

> проверить цену.

---

# 67. Sensitive Data

Документы пользователя должны иметь отдельные правила доступа.

Не передавать их специалистам, которым они не нужны.

---

# 68. Audit

Для expert activity хранить:

- specialist;
- timestamp;
- fields viewed;
- fields changed;
- evidence added;
- result version.

---

# 69. Product Metrics

На MVP отслеживать:

- % пользователей, дошедших до expert request;
- request type;
- % успешно подтверждённых вопросов;
- % проверок, изменивших MatchResult;
- % проверок, исключивших объект;
- время выполнения;
- user decision after expert result.

---

# 70. Главная продуктовая метрика

Экспертный слой успешен не тогда, когда продано больше консультаций.

Он успешен, когда:

> пользователь после проверки принимает решение с меньшей неопределённостью.

---

# 71. Acceptance Criteria

`expert-layer.md` считается реализуемым, если система умеет:

1. создать request из карточки объекта;
2. создать request из comparison;
3. создать request по critical unknown;
4. определить required specialist;
5. передать Context Package;
6. хранить status;
7. сохранить structured result;
8. показать checked/not checked;
9. создать manual evidence;
10. обновить canonical data;
11. пересчитать confidence;
12. пересчитать matching;
13. обработать unable_to_verify;
14. передать задачу другому специалисту;
15. создать onsite request;
16. не путать юридическое заключение с обычным разбором.

---

# 72. Главный принцип для coding-agent

Нельзя строить экспертный слой как:

```text
форма "оставьте телефон"
```

без связи с объектом и уже собранным контекстом.

Правильная архитектура:

```text
UserRequest
     +
Property / Comparison
     +
MatchResult
     +
Unknowns / Conflicts
        ↓
ExpertRequest
        ↓
Specialist
        ↓
Structured ExpertResult
        ↓
Manual Evidence
        ↓
Canonical Data
        ↓
Confidence / Matching Update
```

Главное правило:

> Человек подключается не вместо системы, а в точке, где системе уже понятно, какой именно вопрос невозможно или нецелесообразно решать автоматически.
